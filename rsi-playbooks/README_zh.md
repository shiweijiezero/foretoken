# RSI Playbooks

[English](README.md) | 简体中文

Foretoken 是一个面向 RSI（Recursive Self-Improvement，递归自提升）的推理基础设施框架，支持 Agent 自主修改、部署、评测和优化推理系统。

这套手册提供任务指导、实验方法与可复用经验，并持续吸收经过验证的发现，帮助后续迭代更有效地开展优化。

## 开始优化任务

克隆仓库：

```bash
git clone https://github.com/shiweijiezero/foretoken.git
cd foretoken
```

### Claude Code

在仓库目录启动一个专用于 RSI 的交互会话：

```bash
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude
```

该命令仅在本次会话启用 Agent Teams。在此会话或已启用 Team 的会话中粘贴以下指令；自定义任务只需替换文件路径：

```text
/goal 使用 RSI skill 和 Agent Team，按照 rsi-playbooks/tasks/qwen-decode_zh.md 完成推理系统优化并交付规定结果。先阅读任务、已有实验记录和 rsi-playbooks/guidance/ 中的相关指导。为本任务创建专用 Git worktree，为并行候选分别创建独立 worktree。主 Agent 主动构思和调整方向，按研究问题派工、综合各方发现，统一负责环境准备、部署与并行实验、资源清理和最终集成验收。Worker 研究开发候选、解释改动、分析主 Agent 返回的结果，不自行运行代码。主 Agent 从交付版的对应工作区执行，运行期间不改源码；恢复时核对并复用已有工作区，随新发现推动团队持续协作。执行期间维持任务规定的有效工作人数，及时处理结果和成员的新任务请求。遵守任务的资源、时间预算和结束条件，用户要求暂停或停止时停止推进并完成必要收尾。
```

主 Agent 用同一个 goal 管理整体目标和团队推进，成员按各自职责协作。暂停时，用 `/goal clear` 结束自动续轮，再要求团队停止本任务的实验和采集进程。

Codex 使用自身的原生 `/goal` 维护任务目标，通过 Agent 工具派工与续派。用 `/goal pause` 暂停目标，并要求成员停止本任务的实验与采集进程；用 `/goal resume` 继续。

## Agent 分工

团队以多个 Worker 并行推进优化方向，其他角色围绕它们协作。主 Agent 按任务资源和并行要求配置人数，保留成员上下文以承接后续工作：

| 角色 | 职责与数量 |
| --- | --- |
| 主 Agent | 构思和调整方向、派工、审查候选代码、综合决策，统一负责环境准备、部署与并行实验、资源清理、集成验证和最终交付。 |
| Advisor | 至少两名成员专注研究、瓶颈分析、探索、反馈和反思，熟悉代码与系统，搜索社区寻找灵感，用更广泛的证据质疑局部假设。主 Agent 在预算和运行环境上限内安排人数。 |
| Worker | 研究所分配方向、寻找瓶颈、设计实现改动，分析主 Agent 返回的结果。交付代码与解释，运行由主 Agent 负责。至少安排 1 个 Worker 跟进系统整体执行路径；优先为每个活跃方向安排一个或多个专门 Worker，总人数由主 Agent 决定。 |
| Recorder | 默认 1 名。独立检查候选行为、对照条件和收益归因，统一维护迭代历史、当前总览、证据链接和最终报告；不实现自己审查的候选。 |
| Monitor | 1 个，负责整个 Team 的工作效率和资源利用效率。定期查看任务与成员进展、核对有效并行人数，持续采集 GPU 数据，发现交接延误、重复劳动、等待阻塞或资源闲置时推动处理。 |

成员使用角色加编号或代号命名，例如 `lead-01`、`advisor-01`、`worker-01`、`recorder-01`、`monitor-01` 或 `worker-alpha`。续派沿用稳定名称，具体职责写在任务中。具体命名与派工方式见[共用 skill](../.agents/skills/rsi/SKILL_zh.md#组建团队与派工)。

工作人数包含实际执行任务的 Worker、Advisor 和 Recorder，按成员去重。主 Agent 和 Monitor 不计入，等待、阻塞和已完成成员不算正在工作。主 Agent 按任务要求和运行环境上限安排有效工作，处理人数不足的原因。

给每名 Worker 明确研究问题、范围、预算、预期开发结果和工作区。Worker 自主研究开发，无需等待 Advisor 交方案。Advisor 和 Recorder 直接与 Worker 协作；主 Agent 执行交付的改动，将结果返回供分析和继续开发。审查和记录与独立准备并行，主 Agent 选择保留改动，负责集成验证和最终交付。

成员及时交流会影响他人的发现，分配任务完成或无法推进时请求后续安排。Recorder 统一负责总览和迭代记录，链接原始证据而非重复抄写。恢复时沿用原预算，核对记录与实际结果、进程状态，并补建缺失成员。

### 并行工作区

并行候选使用独立的 Git worktree（同一仓库的独立工作目录），由主 Agent 准备并协调基线、修改者、资源和结果位置。Worker 修改分配的候选；主 Agent 从各候选交付版的对应工作区同步、构建、部署和测量，使用独立的部署身份、可写缓存和结果目录。运行期间保持该工作区不变；继续开发时使用另一 worktree，或等待主 Agent 释放原工作区。只读调研和审查直接读取对应工作区。

实验数量和 GPU 分配取自任务要求。审查者核对各候选的实际代码与结果，主 Agent 决定保留方案后安排集成验证；改动和证据保存、使用者退出后再清理工作区。

## 设计目标

- 快速部署：将代码改动快速更新到目标集群中的推理服务。
- 测试与反馈：验证性能、模型质量和资源开销，了解改动效果。
- 观测与诊断：结合日志、指标和性能剖析，定位运行问题与性能瓶颈。
- 实验记录：关联每轮改动、运行配置、结果和决策，方便比较与复现。
- 参考与经验积累：查找、补充参考资料，将实验经验整理为可复用的指导。
- 行为与归因检查：检查模型实际行为，识别指标投机，判断收益是否确实来自预期改动。

## 使用步骤

一个研究问题可以包含多轮候选迭代，也可以以有依据的“不适用”结论结束。一轮迭代评估一个候选，其负载分组和重复测量属于同一轮。整个优化任务是否完成，仍由目标、预算和结束条件决定。

1. 明确要改善的行为、范围和判断标准。阅读相关代码、研究与历史结果，选择值得深入的问题。
2. Advisor 和 Worker 根据研究与已有证据提出假设；主 Agent 选择对照，在投入较大工作前确认执行可行性。
3. Worker 实现可行候选并解释改动；主 Agent 亲自阅读改动及相关调用路径，审查实现正确性、架构契合程度和生效条件，与 Worker 讨论实现问题。主 Agent 据此选择对照和验证方式，按[源码部署流程](../docs/custom-deployment_zh.md)构建部署，按需进行针对性诊断，在正式测量前确认预期执行路径。
4. 主 Agent 执行选定的[评测](../benchmarks/README_zh.md)，适用时用现有[参数扫描](../benchmarks/docs/recipes_zh.md)，保持对照条件稳定。Worker 分析返回的输出、日志和 profile，与 Advisor 讨论发现并继续修改实现。
5. 由独立 Recorder 阅读实现与原始结果，检查模型行为、对照条件和收益归因。处理审查问题的同时推进不受影响的准备工作，按[实验记录手册](experiment-records_zh.md)保存证据与结论。
6. 依据证据修订或放弃实验候选，由主 Agent 选择经过审查的保留方案、安排组合服务验证。将可复用发现沉淀到指导中，在剩余预算内选择下一项研究问题。

## 选择评测

按本轮优化目标选择评测。命令选择和记录参数见[实验记录手册](experiment-records_zh.md)。

| 评测目的 | 工具与命令 | 查看内容 |
| --- | --- | --- |
| 比较延迟、解码速度和吞吐 | [性能评测](../benchmarks/docs/perf/README_zh.md)，`foretoken perf` | 成功数、延迟分布、TPOT、吞吐及实际输出长度 |
| 评估回答质量 | [质量评测](../benchmarks/docs/eval/README_zh.md)，`foretoken eval` | 得分、样本数、评分方式和逐题回答 |
| 定位计算、通信和等待开销 | [性能剖析](../benchmarks/docs/profile/README_zh.md)，`foretoken perf --profile` | 执行时间线；速度对比另用不带剖析的运行 |
| 比较不同并发、输入长度和流量下的表现 | [参数扫描与负载配置](../benchmarks/docs/recipes_zh.md) | 各负载点的指标及变化趋势 |

命令选项可用 `foretoken perf --help` 和 `foretoken eval --help` 查询。
