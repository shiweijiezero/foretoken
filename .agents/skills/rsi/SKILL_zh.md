# 执行 RSI 任务

[English](SKILL.md) | 简体中文

## 明确任务

所有角色开始工作前，都应先[熟悉 Foretoken](roles/common_zh.md#先熟悉框架)。各成员还应阅读仓库规范、用户提供的任务和相关实验记录，并按当前问题查阅[研究资料](../../../rsi-playbooks/guidance/README_zh.md)。本文件中的相对链接以 skill 所在目录为起点。

只有用户要求执行或恢复任务时，团队才启动实验。新任务需要记录起始时间和截止时间；恢复任务时，则先查看已有作业和结果，继续使用原来的时间预算。主 Agent 从任务中识别标注 `【不可修改】` 的固定条件，并区分可调整的实现选择。给定配置作为比较起点；没有起始配置时，先建立初始方案。团队沿用已有的有效结论继续研究，直到任务规定的结束条件满足。

明确任务后，启用本主会话的[接续绑定](continuation_zh.md#启用本次任务)。项目 hook 只作用于这个 RSI 会话；向成员交付后续步骤需要明确登记。运行环境尚未加载或信任 hook 时，说明限制，并直接处理原生成员完成通知。

研发与环境准备同时启动。Experimenter 准备运行环境和起始测量，Explorer 搜索并分析资料，Worker 推进关键实现和当前能做的本地验证。环境尚未就绪时，优先继续不依赖它的实现和探索；需要真实环境的验证留到就绪后完成。

主 Agent 分配资源前，先按[资源协调说明](roles/common_zh.md#协调资源与运行环境)核对任务涉及的节点、现有使用者和可用 GPU 窗口。节点暂时无法使用时，应记录原因，并处理能够解决的问题。

并行实验开始前，主 Agent 统一 W&B 的命名。同一研究课题使用一个 project，名称以 `foretoken-` 开头，并包含模型、硬件和目标，例如 `foretoken-qwen35-metax-inference`。每次实验使用一个带日期或实验名的 group，各次 run 再区分方案、负载和重复测量。恢复时沿用原名称，并在实验记录中保存运行链接。

主 Agent 在任务开始时按[报告维护流程](../../../rsi-playbooks/experiment-records_zh.md#持续维护用户报告)建立面向用户的 `report.md`，并指定作者，随测量结果和决定持续更新。

## 组建团队与派工

主 Agent 围绕最重要的问题和具有大幅改善潜力的机制组织研究组合，为主攻方向配置持续负责人及研究、实现和实验预算，独立备选与小改进可以并行。不能仅凭就绪、便宜或立即有正收益决定研究优先级。成员在这些分工内持续推进，主 Agent 随证据变化调整整个研究组合。交接与执行见[团队协作说明](roles/common_zh.md)。

分别采用 task 中的 Explorer、Worker、Experimenter 和 Evaluator 数量，都不包含主 Agent。前三项指各角色的并行成员数；未填写时由主 Agent 安排，没有专属成员的职责交给主 Agent 或其他成员承担，这不增加人数，也不构成独立审查。Evaluator 数量指每轮新建的巡查 Agent 数，省略或留空时默认 1。明确填写的数量都应遵守，包括 0；Evaluator 设为 0 表示关闭巡查，不能把主 Agent 自查算作独立巡查。

运行环境的实际并发上限仍然有效，主 Agent 占用的名额也应计入。无法同时容纳用户要求的团队时，按优先级分批安排，记录要求人数、实际人数及差异原因。每名成员在同一时刻只按一个分配的角色计数。

如果任务填写了 `Codex 模型` 或 `Claude 模型`，这些映射就是派工规则：创建成员时传入指定的模型和推理强度，并在团队记录中记录实际值。只有任务没有指定的角色才使用全局默认值。

[Explorer](roles/explorer_zh.md) 持续探索技术机制、优化方法和新的研究问题，并帮助团队反思当前方向。Explorer 独立开展研究，可以探索不同问题，也可以从不同角度研究同一个问题，并在研究过程中持续交流发现。

[Worker](roles/worker_zh.md) 研究具体问题并实现候选方案，再根据实验结果继续改进。实现负责人应跟进完整执行流程，以便把局部改动与服务整体表现联系起来。

[Experimenter](roles/experimenter_zh.md) 管理实验队列与执行资源，主动向 Worker 索取可测版本，构建、评测、记录结果并释放资源。一名 Experimenter 可以管理多个互不冲突的实验。

[Evaluator](roles/evaluator_zh.md) 通过工作记录和会话记录检查团队进度、资源使用和研究深度。每轮都创建不继承对话历史的新 Agent，只向主 Agent 提交发现，不询问或打断其他成员。

派工提供任务、角色说明、源码和证据的绝对路径。新建 Explorer 不继承主 Agent 的对话，以目标、固定条件和研究问题建立独立上下文，已有候选与结论作为可查阅的资料；后续阶段沿用成员自己的研究上下文。执行成员同时接收待实现或验证的方案，沿用 `worker-01`、`experimenter-01` 等名称。Evaluator 只接收任务文件、角色说明和工作目录，自行查找记录，每轮使用新名称，如 `evaluator-r03-01`。团队使用运行环境提供的主 Agent 消息地址。

收到原生完成或空闲通知时，主 Agent 让负责人继续同一研究问题的下一实质阶段、记录真实依赖，或明确改变分工。一次测量或审查结束不等于持续研究职责结束；跨阶段维持任务要求的各角色。为持续成员登记[具体下一步](continuation_zh.md#安排成员的下一步)，Evaluator 和一次性审查成员不登记。根据实验记录、实际耗时和剩余预算分别安排研究与执行，同一问题沿用熟悉它的负责人。

## 定期检查团队状态

按任务文件中的 `Evaluator 数量` 和 `Evaluator 巡查间隔` 安排巡查；例如 `1` 和 `1h` 表示每小时创建一名新 Evaluator。未填写间隔时，主 Agent 先补齐，将提醒记入[团队记录](../../../rsi-playbooks/experiment-records_zh.md#保存团队与会话记录)，并以任务开始时间为基准。提醒只负责创建 Evaluator；成员接续使用原生完成通知和 hook。没有提醒工具时，使用带超时的等待，并注明只在会话运行期间有效。

按 [Evaluator 说明](roles/evaluator_zh.md)每轮创建不继承历史的新 Agent。巡查占用普通并发名额，排期时要留出运行机会。人数超过可用名额时分批完成；名额已满或上一轮未结束时，记录延迟，稍后补做，不堆积轮次或打断实验。

收到 Evaluator 完成通知时，主 Agent 登记巡查起止时间，阅读评估，在已有团队记录中写下自己的判断与决定。延期或不采纳时说明依据，并继续已就绪的工作。暂停、停止、到期或完成时，停用提醒并结束巡查。

结合 Evaluator 的[PGE 机会评估](../../../rsi-playbooks/guidance/meta-knowledge/06-opportunity-assessment_zh.md)反思当前方向与剩余预算。主 Agent 记录自己的决定和后续分工。

## 隔离候选工作区与执行

每名 Worker 使用独立工作区、任务分支和固定实例名，跨轮复用。交付的版本在构建和评测期间保持不变，具体安排见[候选交接](roles/common_zh.md#分开候选准备与评测)。

遵循仓库的[部署与迭代要求](../../../AGENTS.md#deployment-and-iteration)，优先复用已有兼容镜像和准备好的环境（可大幅缩短部署所需时间）。只调整参数时，复用已安装的应用；修改代码时，沿用已有源码平台，缺少时再准备一次，涉及共享平台更新则与管理员协调。首次准备解决模型与数据集访问。

日常 Go、Rust、Python 改动按[源码部署流程](../../../docs/deployment/source_zh.md#部署模型服务)，通过 `deploy -e` 指定候选源码目录，增量更新。[并行候选](../../../docs/deployment/source_zh.md#并行运行候选方案)共享镜像引用，各自保留代码与可写构建状态。部署与评测使用同一个实例名；`perf` 和 `eval` 测量已部署服务，代码改动先通过部署生效，再进行评测。

各候选选择同一个共享[数据目录](../../../docs/features/model-storage_zh.md)复用模型下载，运行缓存和结果分别保存。使用 `foretoken stop` 释放空闲的服务资源，保留可复用的配置和模型引用。候选不再需要时再用 `foretoken delete` 删除；托管模型版本在最后一个引用释放后可能被回收。

## 推进迭代

按已分配研究问题的进展组织迭代：研究机制、实现核心改动、完成集成、评估服务表现。主 Agent 同时看研究组合和执行队列。原型不必每个阶段都立即提速，应利用返回证据继续完善机制或重新判断假设。Worker 持续负责原问题，有价值的配置实验可以并行。执行方式优先参考现有[实验命令](../../../benchmarks/docs/recipes_zh.md)、示例和 CLI help，资源和对照条件应在运行前安排好。

准备或测量受阻时，主 Agent 指定负责人解决阻塞，让其他成员继续不依赖该结果的研究、实现或局部验证。尚无完整 baseline 或 profile 时，可以先准备有依据的候选及其验证方法，再根据实测决定是否采用。

Worker 把可运行、可复现的版本交给负责实验的 Experimenter。优先让不同实验各用一组空闲 GPU，只有需要同一批卡时才一起安排。Experimenter 部署并确认改动生效，完成测试后记录结果，直接发给 Worker 和已指定的审查者。有卡可用时，先查哪些方案已经准备好，再询问缺少的信息。固定负载组合和重复测量可用 sweep 连续执行。

决定保留或集成改动前，主 Agent 阅读实现及相关调用代码，并结合独立检查的意见作出判断。组合后的方案仍需在任务负载下验证。

主 Agent 对照已投入的时间与资源、实测收益和新认识判断研究进展。进展停滞，或 Explorer、Evaluator 提出问题时，重新分析证据，在用户目标内决定继续、调整或停止方向，记录下一问题、负责人、预算、预期证据与复核时间。对于反复出现的执行问题，由相应负责人修复，确认受影响的流程恢复正常后再继续使用。

停止一个方向时，说明证据排除了什么，以及哪些部分仍未实现或测量。上游没有现成选项属于实现约束，不是性能结论。验证当前最好方案时，其他不受影响的研究仍可在剩余预算内继续。

## 采集 GPU 使用情况

Experimenter 在分配的 GPU 主机上运行本 skill 的 `scripts/gpu_usage.py`。主机需要 Python 3.11+，并安装 `nvidia-smi` 或 `mx-smi`；脚本本身只使用标准库。没有仓库工作区的主机只需复制该脚本。采集应通过任务专属的持久会话或已有任务管理器启动，以便在成员分析结果或 SSH 断开时继续运行。

从各主机的仓库根目录执行下列命令前，将 `GPU_RUN` 设为实验结果下的新目录，`GPU_INDICES` 设为本任务使用的宿主 GPU 序号，多个序号用逗号分隔。`DEADLINE` 使用任务的绝对截止时间，并带上 UTC 时区偏移。

```bash
python3 -I .agents/skills/rsi/scripts/gpu_usage.py collect \
  --output "$GPU_RUN" --gpus "$GPU_INDICES" --deadline "$DEADLINE"
```

采集器会打印 PID 和输出目录，默认每 10 秒向 `samples.jsonl` 追加记录；需要改变间隔时，使用 `--interval`。脚本会自动选择已安装的设备工具，主机同时安装两种工具时，可用 `--backend nvidia` 或 `--backend metax` 指定。只有任务使用全部可见 GPU 时才省略 `--gpus`；没有时间预算的任务才省略 `--deadline`。恢复采集时使用新目录，以保留之前的记录。

分析一段已经结束的时间窗口时，将 `WINDOW_START` 和 `WINDOW_END` 设为对应的 ISO 时间。下列命令读取原主机、共享存储或本地副本中的采样，不会中断正在进行的采集。

```bash
python3 -I .agents/skills/rsi/scripts/gpu_usage.py summarize "$GPU_RUN" \
  --since "$WINDOW_START" --until "$WINDOW_END"
```

如果窗口包含多段采集，应传入所有对应目录，包括恢复后的采集目录。命令会按节点和 GPU 汇总时间加权利用率，并避免重复计算重叠或复制的记录。解释结果时，还应检查覆盖率、数据是否及时和查询错误；缺少采样的时段保持未知。

不再需要采集时，在采集主机上执行：

```bash
python3 -I .agents/skills/rsi/scripts/gpu_usage.py stop "$GPU_RUN"
```

停止标记、截止时间或 SIGINT、SIGTERM 都会让采集器在当前查询结束后退出，单次查询最多等待 10 秒。负责人应确认最后的 `end` 记录和进程退出，再释放采集器，并保留样本供报告使用。手工停止进程时，需要核对身份，避免误停已复用 PID 的进程或共享监控。

## 暂停与结束

用户要求暂停或停止，或者任务到期时，主 Agent 先[解除接续绑定](continuation_zh.md#等待暂停与结束)，停止安排新实验并通知团队。各负责人停止自己的进程，确认退出；暂停时保留未完成工作，任务结束时保存所需结果，再清理不再使用的资源。

主 Agent 检查保留的改动和实测结果，包括采样覆盖率与未解决的问题。作者按[报告维护流程](../../../rsi-playbooks/experiment-records_zh.md#持续维护用户报告)更新已有报告，写清暂停或结束时的实际状态与已达到的目标，并向用户提供报告路径。
