# 执行 RSI 任务

[English](SKILL.md) | 简体中文

根据任务和当前运行环境选择协作与持续执行工具。不同环境沿用相同的角色职责，先了解可用的目标管理、委派、消息、任务和监测能力。协调投入与实验需要相称，让团队能明确了解资源归属、进展和停止条件。

## 明确任务

阅读仓库指令、用户提供的任务、[共用流程](../../../rsi-playbooks/README_zh.md)、[执行规则](../../../rsi-playbooks/tasks/README_zh.md)和相关历史实验记录。成员按当前问题从[优化指导](../../../rsi-playbooks/guidance/README_zh.md)选读参考资料与已有经验。相对链接以本 skill 目录为基准。任务参数由任务文件提供，不在 skill 中复制默认值。

任务提供起始配置时，先核对任务要求与当前环境，将其作为可演进的起点，而非固定策略；未提供时，自主探索并记录初始可对照配置。两种情况都承接适用的历史结果、已排除方向和未解决问题。现有候选耗尽时，重新反思方向、研究新方法，而不是自动结束任务。方法根据目标、证据和剩余预算自主选择，完成仍以任务结束条件为准。

先判断用户要求的是执行、恢复、暂停还是讨论。暂停、停止或设计讨论不授权启动实验。新任务在实验笔记中记录起始时间与截止时间；恢复时先读取原预算与资源归属，沿用约定的时间预算。

把任务列出的全部节点纳入实验安排，确认可用资源和现有使用者，按需求分配独立候选。未使用的节点记录具体阻塞并处理可解决的问题。区分整个资源池与单服务上限。

使用 W&B 时，在并行运行前统一易读的命名。`--wandb-project` 对应持续研究的优化课题，以 `foretoken-` 开头，并用模型、硬件和目标标明课题，例如 `foretoken-qwen35-metax-inference`。一次完整 RSI 实验使用一个 `--wandb-group`，以日期或实验名区分，收拢全部迭代和并行候选；`--wandb-run-name` 区分迭代、负载、并发和重复测量。主 Agent 为同一次实验的全部候选使用相同 project 和 group，恢复时沿用原命名；同一课题新开实验时，在原 project 下使用新的 group。在实验总览和迭代记录中保存名称与运行链接，方便 Worker 和 Recorder 查找、对比结果。

## 组建团队与派工

主 Agent 主动构思方案、选择和调整方向、拆解任务、综合结果并作出保留决定，同时统一负责环境配置、代码同步、构建、测试、部署、并行实验、资源清理、集成验证及最终交付。Worker 负责研究、设计、代码和运行结果分析。Advisor 专注探索与反思；Recorder 独立审查结果并维护历史与汇报；Monitor 观察执行效率和资源使用。

主 Agent 主动构思和修正优化方向，而不只是分配已有待办。把成员的局部发现联系成系统层面的理解，考虑其他解释，判断哪些问题值得深入。借助 Advisor 的不同视角反思当前方案，主动推进有价值的问题，不等用户提供下一想法；方法和投入由任务决定。

开始执行时，将以下角色分配给团队成员。给每名 Worker 明确研究开发问题及预期结果，说明允许的代码改动、工作区、剩余预算、结束条件、协作成员和结果位置。实验安排与执行由主 Agent 负责，Worker 交付代码改动与分析。提供[共用角色约定](roles/common_zh.md)、角色文件、任务、适用仓库规范和原始证据的绝对路径，要求成员亲自阅读；相关工作保留上下文。

| 角色指令 | 初始安排与人数 | 记录归属 |
| --- | --- | --- |
| 主 Agent | 构思方案、选择方向、分配开发任务、审查候选代码并作出决策；统一负责环境准备和全部候选执行，包括并行实验与集成验证。 | 实际命令、运行身份、结果、决定和最终交付，由 Recorder 维护记录。 |
| [Advisor](roles/advisor_zh.md) | 至少两名成员研究互补问题，熟悉代码与系统，探索社区思路，提供瓶颈分析、替代方案、反馈和反思。主 Agent 按有效视角、预算和运行环境容量安排人数。 | 向 Worker、主 Agent 和 Recorder 提供研究发现与建议。 |
| [Worker](roles/worker_zh.md) | 负责研究、瓶颈分析、设计、代码修改及主 Agent 返回的结果分析。至少 1 个 Worker 研究端到端代码路径；多名 Worker 并行开发候选，主 Agent 统一运行实验。 | 向主 Agent 和 Recorder 提供候选代码、改动说明与结果分析。 |
| [Recorder](roles/recorder_zh.md) | 默认 1 名，独立检查候选行为、对照条件和收益归因，统一维护记录，并结合 Advisor 的研究沉淀可复用发现。不实现自己审查的候选。 | 实验总览、迭代与决策历史、证据链接和最终报告。 |
| [Monitor](roles/monitor_zh.md) | 1 个，负责整个团队的工作效率和资源利用效率，包括任务交接、重复劳动、等待阻塞、有效并行和 GPU 持续采集。 | 向 Recorder 提供采集记录和证据。 |

成员使用小写的 `<role>-<编号或代号>` 命名，角色前缀为 `lead`、`advisor`、`worker`、`recorder` 或 `monitor`，例如 `lead-01`、`advisor-01`、`worker-01`、`recorder-01`、`monitor-01` 或 `worker-alpha`。名称标识成员，不绑定方向或任务；同角色续派时沿用原名，团队内保持唯一。若 harness 固定了主 Agent 的消息地址，保留实际地址，不假定可以重命名。

按问题能否独立推进来拆分开发，Worker 在代码修订和结果分析中保持上下文，主 Agent 统筹候选集成与执行。每项资源生命周期有明确负责人，每个文件或划分清楚的章节只有一个写入负责人。

执行期间，主 Agent 持续维护实际工作人数和有效任务，最小、最大人数从任务读取。Worker、Advisor 和 Recorder 仅在实际执行分配任务时计入，按成员去重。主 Agent 和 Monitor 不计入，等待、阻塞和已完成成员不算正在工作。交接或依赖变化时，通过原生任务状态与消息核对；缺少证据的时段标为未知，不据此宣称精确活跃数或时间加权平均值。遵守 harness 上限、任务预算和用户停止要求。有效工作不足时报告真实阻塞。暂停或终止任务时停止人数维护，完成仍以优化结束条件和规定交付为准。

通过团队选用的协作工具明确任务、依赖和资源预留，说明成员是否可以自行认领已就绪且无人负责的工作。主 Agent 回收已完成实验的配额，资源可用后及时启动已就绪候选。在任务结束条件满足前持续推进有效工作。临近截止时，根据已观察到的耗时和依赖，选择剩余时间内能完成分析与交付的工作。报告更新、保留方案验证和闲置资源清理随迭代进行，与独立研究和实验并行；最终验证期间，其他成员继续推进独立工作。

重启后读取实验记录、原预算、资源与进程归属和原生任务状态，确认哪些成员仍存在。harness 未恢复的成员重新创建，并重新分配未完成工作；保留原笔记和预算，不把保存的成员名称当作仍在运行的证据。

## 并行 worktree

并行代码改动和实验候选使用独立 Git worktree。可按成员划分，也可由一个候选组共享工作区并明确文件归属。只读调研和审查可直接读取对应 worktree。主 Agent 通过原生 Git 工具协调创建，在已有实验总览中记录基线、分支、绝对路径、负责成员、资源分配和结果位置。

把开发 checkout 和结果位置交给 Worker。主 Agent 从该 checkout 构建、部署和验证交付的候选，并统一管理远端同步。并行实验通过已有部署机制使用独立的部署身份、可写运行缓存和结果目录，适用时复用只读模型数据。Worktree 隔离源码改动，实验并行数量由任务资源分配决定；GPU 数与实验组数从任务读取。

主 Agent 在并行部署候选前，按[源码部署指南](../../../docs/custom-deployment_zh.md)统一准备支持该部署流程的 CLI，并安装或升级共享源码平台。主 Agent 从各候选交付的 Foretoken worktree 执行 `foretoken deploy`，使用独立 namespace；从其他目录执行时，用 `-e` 指定候选 checkout，并提供部署目录的绝对路径。需要修改引擎时，用 `--engine-source` 绑定各候选独立的引擎 checkout，后续部署沿用该 worktree 记录的选择。CLI 按 checkout 隔离并复用编译缓存。控制器、CRD 或共享平台改动统一通过显式安装更新，不为每个候选重装平台。

Worker 并行推进独立代码改动，主 Agent 在任务资源预算内并行准备和运行候选。远端执行优先使用本任务的 tmux 会话或已有远端任务管理器，不按预计时长划分；简单的一次性查询可直接使用 SSH。日志和实际命令退出状态保存在远端，记录会话或任务身份。断连后先查看已有任务，再决定继续或重新启动。利用完成通知，让方向构思和其他实验持续推进。构建和测量期间保持候选源码及运行环境不变，需要继续开发时使用另一工作区。复用候选环境与缓存，资源释放后及时安排下一项已就绪工作。

测量或审查前，确认候选的实际源码和运行配置，包括未提交改动。审查者读取对应候选，而非主 Agent 的工作区。主 Agent 选择保留改动，将代码集成交给 Worker，处理跨方向取舍，并执行组合方案验证。协调共享 Git 操作：worktree 的索引独立，分支和 stash 属于同一仓库。

候选改动和证据已保存或明确放弃，且成员、构建和服务都不再使用后，再删除实验 worktree。暂停时保留未完成工作，恢复时明确复用或重新分配工作区。

## 推进迭代

[Worker 工作流程](roles/worker_zh.md)涵盖研究、设计、代码修改和返回结果的分析。主 Agent 连接开发与执行：

1. 与 Advisor、Worker 共同提出假设并判断优先级。安排执行前，查阅[部署指南](../../../docs/custom-deployment_zh.md)、[实验命令示例](../../../benchmarks/docs/recipes_zh.md)、维护中的配置示例和相关 CLI help，复用已有的部署、参数扫描、剖析、记录和结果比较能力。分配独立代码改动，在研究继续开展时准备共享环境。
2. 亲自阅读交付候选的代码改动及相关调用路径，审查实现正确性、与系统架构的契合程度及改动生效的条件。与 Worker 讨论实现问题，明确每项实验要回答的问题及结果将影响的决定，结合审查后的代码和已有结果选择对照与验证方式。
3. 构建并部署候选，按需进行针对性诊断，在正式测量前确认预期执行路径。确定的测量组合使用现有 sweep 连续运行，资源允许时并行开展独立候选。
4. 将每次完成的结果和运行配置交给对应 Worker 与 Recorder。Worker 分析并修订代码，Recorder 独立审查并更新迭代历史、摘要和汇报；向 Advisor 分享发现，继续从整体反思。
5. 根据结果决定保留、修订或放弃候选，选择下一问题。分配代码集成，让组合验证与独立工作并行。随新发现调整方向、人员和资源安排。Monitor 或实验记录发现反复出现的执行障碍时，先区分使用和环境问题与框架缺陷。主 Agent 修正环境，在任务范围内将值得修复的代码问题交给 Worker，验证受影响的流程后复用。

进展与交接遵循[角色协作约定](roles/common_zh.md)，阶段结果返回后继续已授权的开发。恢复时先核对实际结果和运行进程，再由主 Agent 继续执行。

## 采集 GPU 使用情况

在每台 GPU 主机上使用本 skill 的 `scripts/gpu_usage.py`，需要 Python 3.11+ 及已安装的 `nvidia-smi` 或 `mx-smi`。脚本只依赖标准库；主机没有 checkout 时只需复制该脚本。使用现有远端任务管理器或本任务专属的持久 shell 会话，让采集在Monitor 分析期间及 SSH 断开后继续运行。

在各主机的仓库根目录，将 `GPU_RUN` 设为实验结果下的新运行目录，`GPU_INDICES` 设为该节点分配给本任务的宿主 GPU 序号（逗号分隔），`DEADLINE` 设为带 UTC 偏移的绝对 ISO 截止时间。启动一次：

```bash
python3 -I .agents/skills/rsi/scripts/gpu_usage.py collect \
  --output "$GPU_RUN" --gpus "$GPU_INDICES" --deadline "$DEADLINE"
```

采集器打印 PID 和输出目录，此后默认每 10 秒向 `samples.jsonl` 追加数据。用 `--interval` 调整采样间隔。脚本自动选择已安装的设备工具；两种工具都存在时，用 `--backend nvidia` 或 `--backend metax` 指定。仅在任务拥有全部可见 GPU 时省略 `--gpus`，仅在任务没有时间预算时省略 `--deadline`。已有采样文件不会被覆盖，恢复采集使用新目录。

定期分析时，将 `WINDOW_START`、`WINDOW_END` 设为下一个已完成窗口的 ISO 时间。可在原主机、共享存储或Monitor 机器上的记录副本中读取数据；汇总不会启动或中断采集：

```bash
python3 -I .agents/skills/rsi/scripts/gpu_usage.py summarize "$GPU_RUN" \
  --since "$WINDOW_START" --until "$WINDOW_END"
```

传入同一时间窗口内的各段采集目录，包括恢复后的目录。命令按节点和 GPU 汇总时间加权利用率，重叠或复制的数据不重复计数。结合覆盖率、数据新鲜度和查询错误判断结果；缺失数据保持未知，不计为空闲。

在采集主机上请求停止：

```bash
python3 -I .agents/skills/rsi/scripts/gpu_usage.py stop "$GPU_RUN"
```

停止标记、截止时间、SIGINT 或 SIGTERM 会使采集在当前查询完成后退出，查询最长 10 秒。确认最后的 `end` 记录及进程退出，再释放采集器。保留原始数据用于实验报告；恢复时使用新目录。不向已复用的 PID 发送信号，也不停止共享监控。

## 暂停与结束

用户暂停、停止和任务截止时间优先于排队消息、新任务请求及人数目标。停止安排实验，通知成员，由资源负责人停止进程并确认退出，必要时使用原生取消操作。暂停时保留可恢复的工作；完成时，在保存证据后安排清理已无使用者的资源。

按[实验记录手册](../../../rsi-playbooks/experiment-records_zh.md)，由指定作者在任务要求的路径完成交付。主 Agent 验收并汇总保留改动、实测结果、GPU 采样覆盖和未解决的阻塞。角色指令和历史验证记录不作为当前团队、实验或监督已运行的证据。
