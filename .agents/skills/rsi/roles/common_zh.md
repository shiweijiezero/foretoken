# RSI 团队协作

[English](common.md) | 简体中文

Worker 提出并实现改动后，会把待验证的代码或配置作为候选方案交给 Experimenter。Experimenter 在分配好的环境中运行实验，把结果返回给 Worker，供其解释和继续改进。与此同时，Advisor 持续研究技术机制和新的方法，主 Agent 则结合各方发现调整研究方向、优先级和资源安排。

同一问题的后续工作尽量交给熟悉它的成员继续。这样既能减少重复了解背景的时间，也能让成员根据前面的发现逐步深入，而不是每轮从头开始。

## 先熟悉框架

主 Agent、Advisor、Worker 和 Experimenter 都应在开始各自工作前，先熟悉 Foretoken 的整体设计和使用方式。从[项目 README](../../../../README_zh.md)入手，结合架构说明、相关组件文档和维护中的示例，了解控制面、数据面、推理引擎与评测工具之间的关系，以及服务如何部署、请求如何执行、评测与结果记录如何完成。

在此基础上，每名成员再围绕自己的问题阅读相关源码、配置和历史实验，弄清框架已经具备的能力，以及本次工作可能影响哪些部分。主 Agent 提供所需资料的路径，成员自行阅读原文并结合实现核对。相关版本或任务范围变化后，再补充了解受影响的部分。

## 分配完整的问题

主 Agent 分配任务时，需要说明希望回答的问题、已有结论，以及这项工作将帮助团队作出什么决定。同时，应提供相关代码、参考配置和实验记录的位置，让负责成员阅读原文，了解方案的适用条件和仍未解决的问题。

成员还需要知道可以修改哪些部分，比较时应保持哪些负载、精度和生成设置，以及能够使用多少时间和资源。每项实验都要明确执行者、工作区、部署环境和结果位置。完成这些安排后，成员便可以在范围内连续推进，无需为每条命令等待批准；如果下一步需要额外资源、修改共享环境或改变对照条件，再由主 Agent 协调。

成员将完整方案写入 `<output-dir>/iterations/<name>/notes/`，`<output-dir>` 为实验结果目录。首次交流提供摘要和完整文件路径，相关成员阅读方案、代码与依据，充分讨论思路和验证计划，并记录形成的决定与未解问题。目录组织见[文档协作说明](../../../../rsi-playbooks/experiment-records_zh.md#通过文档共享方案与代码)。

## 分开候选准备与评测

如果候选准备和实验执行由不同成员负责，就把它们记为两项有依赖关系的任务。Worker 除了交付可复现的代码版本，还要解释改动、预期效果和比较方法，并提供参考结果、负载与运行要求。交接时明确哪些组件需要重新构建或重启，哪些模型进程和缓存应继续保留。这些信息齐备后，Experimenter 才能判断如何部署和评测该方案。

候选交付后，从排队、构建到测量结束，工作区源码和运行环境都保持不变；评测结束后再复用该工作区推进下一轮。只有确实需要同时开发下一版本时，才另设开发目录或独立待测副本。

主 Agent 从同一份任务记录中查看准备中、等待评测和正在评测的候选数量，并分别调整准备与评测的并发。准备耗时较长、评测资源经常空闲时，可以让 Worker 提前准备少量彼此独立的方案；等待评测的方案已经很多时，则减少新准备，把精力放在解释已有结果或完善尚未交付的方案上。调整时还要考虑剩余预算，给评测和结果分析留出时间。

运行环境提供任务工具时，使用其中的负责人、依赖和完成状态。若工具能够防止多个成员重复认领同一任务，且主 Agent 已分配相应资源，成员可以自行接手就绪工作。否则，由主 Agent 明确指派负责人。没有任务工具时，在对应的迭代笔记中记录这些安排。

## 协调资源与运行环境

主 Agent 在任务记录中登记每个部署的负责人、节点、资源预算和使用时段。共享主机的 GPU 由管理员结合宿主进程与 Kubernetes 负载确认可用情况；共享平台和驱动变更也由管理员协调。

按节点当前可分配资源和已有 Pod requests，为服务、构建、模型与数据准备、评测客户端安排预算。需要时调整[原生构建并发](../../../../docs/deployment/source_zh.md#修改推理引擎)。

资源允许时，准备与评测可以并行。最终对照前，与共用节点、存储或网络的任务负责人约定测量时段，结束或暂停本任务的竞争负载，再在相同条件下测量参考方案和保留方案。

相关进程和服务退出后再释放资源；仍在运行的作业与采集器由接收方确认接手。SSH 断开后，先检查原作业，再决定是否重启。

## 随实验返回结果

已经确定的负载组合和重复次数可以交给现有 sweep 连续执行。远端实验使用任务专属会话或已有任务管理器保存日志和退出状态，便于在断连后继续检查。分析结果时，应分别确认测量是否结束、请求是否成功，以及结果是否满足任务要求。

Experimenter 完成一组测量后，将结果直接发给需要它的成员，并说明记录位置、资源状态和下一步安排。如果有事项需要主 Agent 决定，应同时说明原因。主 Agent 收到结果或依赖变化后，先处理由此产生的调度问题，让已就绪工作继续运行，再回到自己的研究。成员遇到局部阻塞时，也可以先推进范围内不受影响的工作。

Experimenter 维护所负责的迭代记录，主 Agent 指定一名作者更新报告。摘要应链接原始记录，让读者能够追溯结论；输入和条件没有变化时，可以继续使用已经核验的结果。具体记录方式见[实验记录手册](../../../../rsi-playbooks/experiment-records_zh.md)。

## 独立复核结论

在决定保留方案之前，主 Agent 请一名没有参与该方案实现和运行的成员检查结果。审查者需要结合实际代码、运行配置和原始数据，确认实验确实使用了预期的改动。随后，再检查精度、负载、输出设置和资源分配是否适合比较，以及失败请求、缓存、预热或其他负载是否影响了结论。

如果现有证据还不能解释某个具体问题，审查者应说明需要什么对照来澄清它。Experimenter 将审查意见与开发者的解释分别记入实验记录，主 Agent 据此决定是否继续研究、保留或集成该方案。

## 交接与恢复

一项工作结束时，负责成员应说明得到了什么结论、结果保存在哪里、还有哪些问题，以及哪些进程和资源仍在使用。后续工作已经包含在原分配中时，可以继续推进；需要改变范围或增加资源时，向主 Agent 提出建议。恢复任务时，先核对已有记录、远端作业和成员状态，再沿用原预算与已经完成的结果继续工作。

用户要求暂停或停止，或者任务到期时，主 Agent 停止安排新实验，各负责人停止或交接自己的作业并保存结果。GPU 采集器的 deadline 只控制采集进程，其他作业仍需要各自停止。

有效工作人数按实际开展任务的 Worker、Experimenter 和 Advisor 统计，每名成员只计一次。主 Agent，以及正在等待、受阻或已经完成任务的成员不计入。缺少记录、无法判断的时段应注明未知。
