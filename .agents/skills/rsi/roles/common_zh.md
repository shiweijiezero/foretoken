# RSI 团队协作

[English](common.md) | 简体中文

Worker 提出并实现改动后，会把待验证的代码或配置作为候选方案交给 Experimenter。Experimenter 在分配好的环境中运行实验，把结果返回给 Worker，供其解释和继续改进。与此同时，Explorer 持续研究技术机制和新的方法，主 Agent 则结合各方发现调整研究方向、优先级和资源安排。

## 先熟悉框架

研究与执行成员先阅读[项目 README](../../../../README_zh.md)、架构说明、相关组件文档和维护中的示例，了解控制面、数据面、推理引擎与评测工具怎样协同完成服务部署、请求执行和结果产出。

再围绕分配的问题阅读源码、配置和历史实验，弄清可复用能力和受影响的执行路径，按主 Agent 提供的位置查阅原文并核对实现。同一问题尽量由熟悉它的成员持续推进，复用已有理解和证据，按资料变化或新判断的需要补读。版本或任务范围变化后，刷新受影响的认识。[Evaluator](evaluator_zh.md) 每轮以新身份从任务、角色要求、上次发现与本期变化开始，需要判断不熟悉的框架路径时再补读原文。

## 分配完整的问题

围绕每个问题，明确下一项判断及足以支持它的最低成本证据。先复用相关资料、已准备的环境和可比结果，再开展新工作。现有证据仍有具体疑问时，才扩大源码阅读、构建或测量范围；固定扫描也只继续能帮助判断的测量点。

主 Agent 分配需要持续推进的研究问题，明确负责人、已有认识、未解问题，以及相关代码、资料和实验记录。负责人跟进调查、实现和结果分析，也安排等待结果期间可以继续的有用工作。环境准备与研发分别安排，Explorer 和 Worker 同时推进源码分析、实现和已有条件下的验证。

分配任务时，说清楚可以改什么、哪些负载和生成设置要保持不变，以及能用多少时间和资源。研究本来就要验证未知的收益，不要求先证明加速才动手实现。实验也要明确由谁运行、使用哪个工作区和环境、结果保存在哪里。成员在这些约定内自行推进；需要改变优先级、资源预算、共享环境或比较条件时，再请主 Agent 协调。

完整方案保存在 `<output-dir>/iterations/<name>/notes/`，其中 `<output-dir>` 是实验结果目录。共享文件和写作分工见[文档协作说明](../../../../rsi-playbooks/experiment-records_zh.md#通过文档共享方案与代码)。

## 直接交流，减少等待

例如，Explorer 找到一种可能更快的方法，可以直接把发现和资料发给研究这个问题的 Worker；Worker 准备好代码后，直接请负责该方案的 Experimenter 测试。审查者也把具体问题交给能修改代码或补做实验的人，不必都经主 Agent 转述。

简短结论、问题和协调事项直接发消息。长说明、完整依据或需要多人阅读的内容先写入共享文件，再发一句摘要和准确路径。第一次说明背景，后续只补充变化，不把整篇文档反复复制到消息里。文件位置和作者分工见[记录手册](../../../../rsi-playbooks/experiment-records_zh.md#通过文档共享方案与代码)。影响全体的变化再通知全体；如果发现正在运行的实验会得出无效结果，应立即提醒执行者。

Evaluator 独立读取工作与会话记录，只向主 Agent 提交评估，指出偏差和需要决定的问题。主 Agent 据此反思，再决定是否改变方向、资源或分工。

等待答复时，先做不依赖这条答复的工作。确实无法继续时，说清楚缺什么、需要谁提供。日常进度消息不必逐条回复，已有完成通知的任务也不必反复催问；移交 GPU 或正在运行的作业时，仍要确认有人接手。主 Agent 从共享记录了解进度，在需要调整方向、工作范围或资源时介入。

结合会话时间线，留意反复解释、转述、交接和重新理解背景花掉的时间。沟通挤占研究或拖慢实验时，合并交流、减少过细的任务拆分，让熟悉问题的人持续负责。按实际耗时和工作受阻情况判断，不只数消息条数。

## 分开候选准备与评测

Worker 准备待测版本，Experimenter 运行实验，两项工作的先后关系记在任务中。Worker 交付代码时，说明要验证什么、与哪个结果比较、运行什么命令和负载，以及需要几张卡、放在哪些节点。同时说明要重新构建或重启哪些组件，哪些进程和缓存应继续使用，方便 Experimenter 直接安排实验。

候选交付后，从排队、构建到测量结束，工作区源码和运行环境都保持不变；评测结束后再复用该工作区推进下一轮。只有确实需要同时开发下一版本时，才另设开发目录或独立待测副本。

每个候选只由一名 Experimenter 负责，同一研究方向尽量沿用原成员。它在现有任务工具或迭代笔记中维护候选的准备、就绪和运行状态，以及该组作业、服务、采集器和资源状态，链接已完成结果。共享资源记录需要一名作者时，有专职 Experimenter 就由其中一人维护，其他执行者提供变化。记录负责人随工作一并交接，主 Agent 据此决定优先级、预算和跨组安排。

例如，五名 Worker 可以同时准备方案，即使只有两张 GPU。Experimenter 按优先级和可用资源，运行两个单卡实验或一个双卡实验，其他 Worker 继续工作。暂时跑不了的方案，要写明还缺什么；优先级较高的多卡实验，应在设备空出时安排连续的测量时间。GPU 空闲时先查记录，再向 Worker 询问缺少的版本或预计完成时间；需要调整研究安排时，再请主 Agent 决定。

实验共用 GPU 或合用其他组的卡时，由一名 Experimenter 安排使用顺序，其他组照常推进；换人执行前先确认交接。候选积压时，减少重复对照，Worker 继续研究和分析已有结果。

## 协调资源与运行环境

如果有六张符合要求的空闲 GPU，三个双卡实验就可以各用两张，不必轮流等卡。在任务预算内，优先这样安排互不占用对方 GPU 的实验。每组卡由一名 Experimenter 管理，一名 Experimenter 也可以管理多组。连续实验尽量沿用同一组卡和同一负责人，各自完成部署、测量和清理；卡不够时再排队。

使用 GPU 前，Experimenter 检查宿主机进程和 Kubernetes 工作负载，确认设备在任务允许使用的范围内且没有被别人占用，并记录本次实际用了哪些卡。没有准备好接着运行的实验，就释放 GPU；下次使用前重新检查，不为尚未准备好的实验预约卡。共享平台和驱动变更仍由管理员协调。

按节点当前可分配资源和已有 Pod requests，为服务、构建、模型与数据准备、评测客户端安排预算。需要时调整[原生构建并发](../../../../docs/deployment/source_zh.md#修改推理引擎)。

资源允许时，准备与评测可以并行。最终对照前，与共用节点、存储或网络的任务负责人约定测量时段，结束或暂停本任务的竞争负载，再在相同条件下测量参考方案和保留方案。

测量结束后，继续已就绪的实验，或停止不再使用的服务进程、释放 GPU 分配；分析和审查可使用已保存结果继续进行。保留可复用镜像、构建缓存和模型引用。仍在运行的作业与采集器也可由接收方确认接手。SSH 断开后，先检查原作业，再决定是否重启。

## 随实验返回结果

已经确定的负载组合和重复次数可以交给现有 sweep 连续执行。远端实验使用任务专属会话或已有任务管理器保存日志和退出状态，便于在断连后继续检查。分析结果时，应分别确认测量是否结束、请求是否成功，以及结果是否满足任务要求。

Experimenter 对一次运行的责任持续到结果交付与资源释放。安排对照时，主 Agent 指定 Worker 和报告作者，需要独立审查的对照同时指定审查者。每次运行结束，Experimenter 读取实际结果，将原件保存到约定的可访问位置，再把同一份结论和链接直接交给这些接收者；诊断控制即使保存在 benchmark 的 `runs/` 目录外，也属于交付内容。具体内容与远端恢复方式见[完善实验说明](../../../../rsi-playbooks/experiment-records_zh.md#完善实验说明)。

每个测量点完成就交付，不等整组负载跑完。Worker 先分析已有证据，Experimenter 继续剩余测量，未完成项明确标注。已安排的审查者核验结论，作者更新报告，不必每个点都等主 Agent 重新派工。接收者空闲时，使用 harness 的原生 follow-up；只有主 Agent 能调用时，由它接续。消息或 queued step 本身不会恢复空闲成员。

尚未交付的结果仍由 Experimenter 或明确接手的人负责。在已有迭代笔记中记录缺少的访问条件和下一行动负责人。优先级、预算、比较条件及是否保留的变化由主 Agent 决定，其他工作继续。输入和适用条件未变时，可以复用已有审查结果。

## 独立复核结论

根据改动对模型输出的影响选择验证。输出不受影响，或已有质量证据仍适用时，说明依据并复用结论。只有可能影响输出且证据不足时，才按任务约定的预算与频率验证受影响的行为，必要时进行质量评分。

在决定保留方案之前，主 Agent 请一名没有参与该方案实现和运行的成员检查结果。审查者需要结合实际代码、运行配置和原始数据，确认实验确实使用了预期的改动。随后，再检查精度、负载、输出设置和资源分配是否适合比较，以及失败请求、缓存、预热或其他负载是否影响了结论。

如果现有证据还不能解释某个具体问题，审查者应说明需要什么对照来澄清它。Experimenter 将审查意见与开发者的解释分别记入实验记录，主 Agent 据此决定是否继续研究、保留或集成该方案。

## 交接与恢复

阶段交付说明结论、证据和下一项有价值的工作，负责人继续推进分配范围内的任务。确实需要某项结果或决定时，写明依赖和恢复条件。研究问题已有答案时，再交代未解问题与仍在使用的资源。

收到原生完成或空闲通知后，主 Agent 对照任务要求检查当前各角色人数，用具体的下一项任务恢复熟悉问题的成员，另行分配负责人，或记录真实依赖及结束该项职责的理由。Explorer 转去实现或复核时，按实际角色计数，并继续安排探索负责人。恢复整个任务时，先查记录、作业和成员，沿用原预算与已经完成的结果。

用户要求暂停或停止，或者任务到期时，主 Agent 停止安排新实验，各负责人停止或交接自己的作业并保存结果。GPU 采集器的 deadline 只控制采集进程，其他作业仍需要各自停止。

有效工作人数按实际开展任务的 Worker、Experimenter、Explorer 和 Evaluator 统计，每名成员只计一次。Evaluator 只在巡查期间计入，两轮之间不计入。主 Agent，以及正在等待、受阻或已经完成任务的成员不计入。缺少记录、无法判断的时段应注明未知。
