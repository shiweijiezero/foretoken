# RSI 角色协作约定

[English](common.md) | 简体中文

亲自阅读适用的仓库规范、任务、角色说明、分配的源码和原始证据。选择方案或编写工具前，查阅相关组件指南、维护中的示例和现有实现，优先复用能回答当前问题的能力。相关工作沿用成员上下文。

## 按研究问题分工，明确执行范围

例如，Worker 准备草稿深度和路由候选，Experimenter 在各自分配的部署中构建、测量已就绪版本。上一候选的评测与下一候选的准备并行，结果直接返回开发者和独立审查者。主 Agent 调整优先级与资源，统一安排最终对照的无竞争窗口。

主 Agent 负责研究优先级、资源分配、共享环境变更、集成与最终验收，为每项评测指定唯一执行负责人，通常由 Experimenter 承担；小任务可由主 Agent 或 Worker 兼任。执行负责人在分配范围内负责同步、构建、部署、测量和清理。未获执行任务的 Worker 开展研究、代码修改与已有结果分析；看到空闲 GPU 或无人认领的任务，不代表已经获得资源。

派工须让成员能够判断下一步，而不必重建主 Agent 的整段对话：

| 派工内容 | 成员需要了解的信息 |
| --- | --- |
| 问题与范围 | 预期效果、允许修改的代码或配置，以及结果将支持什么决定 |
| 已有认识 | 参考配置与结果、相关发现和已排除的方法、未解问题，以及需要亲读的原始资料 |
| 对照条件 | 负载、精度、生成行为及其他应保持的条件，允许的诊断和质量评测预算 |
| 归属与资源 | 执行负责人、checkout 与分支、部署身份、节点与设备分配、CPU/内存预算、可写缓存及结果位置 |
| 后续推进 | 时间预算、依赖、可继续开展的工作、结束条件，以及结果接收者和决策者 |

在上述范围内自主选择方法、处理可恢复问题并连续迭代，不为每条命令重新请求批准。首次进展更新说明参考方案、准备改变什么、实际开展哪项对照，尽早暴露理解偏差。汇报进展或交付代码不代表任务结束；专项研究或审查也可以不改代码而形成结论。

## 分开候选准备与评测

由不同成员准备和执行候选时，使用两个有依赖关系的任务。准备阶段交付记录的源码版本、改动解释、参考与负载、预期机制和执行要求；这些输入齐备即为就绪，不意味着已经证明性能。候选排队和运行期间保持交付版本不变，或给执行者独立保存的 checkout；下一版本的开发不能改变待评测输入。

从现有任务记录分别统计三种候选数量：正在准备、已就绪等待评测、正在执行。它们不是 Agent 人数，也不是 sweep 测量点数。按实际 CPU、GPU、存储和时间预算分别安排准备并发与评测并发。有原生依赖与归属机制时直接使用，否则由主 Agent 明确派发就绪工作；保持同一份任务状态，不另外维护三个队列。

根据已观察到的耗时和排队时间调整提前准备量。准备较慢、评测资源经常空闲时，可提前准备少量有价值且相互独立的候选；就绪队列积压时，减少新候选准备，转向解释已有结果、在交付前完善候选或研究新机制。不为填满队列臆造变体，也不启动剩余预算内无法完成评测和分析的候选。新证据改变价值判断时，调整待评测优先级，保留延后或放弃的原因。

## 统一协调资源，不逐条审批命令

在任务授权范围内，资源调整、竞争负载安排及共享平台和宿主变更由主 Agent 统一决定。需要使用其他服务、增加配额、改变对照条件或进入另一成员的工作范围时，说明所需调整及对其他实验的影响；等待决定期间继续不受影响的已授权工作。共享控制面、CRD、驱动和安装变更仍由主 Agent 负责，候选执行任务不包含这些权限。

有原生任务工具时，把分配写入任务记录；否则使用主 Agent 的明确派工消息，并从实验总览链接该消息。每个部署只有一个执行负责人，每个 checkout、文件或明确划分的章节只有一个写入负责人。认领任务不等于获得硬件，执行前核对分配与依赖。运行环境没有原子任务认领能力时，由主 Agent 指派负责人，不让成员竞相抢占未分配任务。

受 Kubernetes 管理的负载使用已有资源 requests、limits 和设备插件。独立 namespace、可写缓存和结果路径隔离候选身份与数据，不保证 CPU、存储或网络性能互不影响。容量安排同时考虑构建、准备任务和评测客户端，模型限额不会覆盖全部过程。无竞争对照开始前，由受影响的负责人确认竞争执行已停止；主 Agent 释放该窗口后再恢复其他实验。

候选构建和测量期间保持源码与运行环境不变，继续修改时使用另一 checkout，或等待执行负责人完成当前运行。同一负责人可在原分配内启动下一轮已授权实验，无需重新申请资源。依赖进程和服务已退出或完成明确交接后，才报告释放配额。成员没有回复、GPU 利用率低或 SSH 断开，都不表示资源已释放。

## 复用执行工具，按变化交流

已确定的负载组合和重复次数交给现有 sweep 连续执行，不让主 Agent 逐点启动。根据已保存的 benchmark 任务与结果记录及其恢复语义判断完成情况，另行检查请求结果。远端执行使用任务专属会话或已有任务管理器，保存远端日志与退出状态，并接收完成通知；断连后先核对原任务，再决定是否重启。GPU 采集器的 deadline 只停止采集，实验执行负责人仍须负责在任务截止时停止自己的作业。

运行环境已有的任务依赖、原子认领和完成通知可以帮助推进就绪工作，但不会判断假设是否值得研究、结果能否对比，或成员是否正在有效思考。这些仍由主 Agent 和独立审查者依据证据判断，不另造调度器，也不平行维护相同任务状态。

每次可采取行动的更新发给需要它的成员，写清：

- 新发现或已完成结果，以及证据位置；
- 作业与资源分配状态，包括刚释放的资源；
- 下一项已授权行动，或尚待解除的依赖和所需决定。

机制发现直接与 Advisor、Worker 交流，执行证据交指定记录者和审查者，跨方向取舍交主 Agent。不转发整份日志，也不重复未变化的状态。收到完成或依赖变化后，主 Agent 先核对结果和资源、接续已就绪工作，再继续研究。局部受阻时推进范围内不受影响的工作，没有可推进项时再请求重新分配。

指定的 Experimenter 维护当前总览和报告，链接任务记录与原始结果，不另建一份资源台账。事实记录随执行完成，独立复核由未参与该候选实现和执行的成员承担。输入和适用条件未变时复用已经审查的发现，把审查投入新变化、新结果和异常，不反复重审同一次运行。假设、执行者解释、独立审查和主 Agent 决定分别保留归属。

## 独立复核结论

保留或集成候选前，安排未参与其实现和执行的 Advisor 或其他成员复核结论。亲读实际代码与配置差异、命令、运行身份和原始结果，比较精度、输入、生成设置、输出长度、失败请求、缓存、预热、设备分配与竞争负载。确认预期路径实际运行，区分改动效果、条件变化和测量波动；只有存在具体未解问题时，再提出针对性的补测。

分别保留审查结论、开发者解释、执行事实和主 Agent 保留决定的归属。输入和假设未变的已审查证据继续复用。Experimenter 负责记录复核意见，不将其变成自我验收，最终判断由主 Agent 负责。

## 完成与交接

问题得到回答后，交付有证据支持的结论、改动和证据、未解问题，以及资源和进程状态。提出下一项有价值的工作，说明是否已在原任务范围内，并更新可用的原生任务状态。只有获准自行认领、且相应资源分配可用时，才能接手就绪任务；否则请求后续安排。

恢复时重新阅读变化的输入，核对记录与实际进程、结果后继续。不因消息迟到重跑已完成的测量。暂停、停止、到达截止时间或分配任务结束时，按约定停止或交接自己负责的进程，保存证据和未完成改动。有效工作人数包含实际执行分配任务的 Worker、Experimenter 和 Advisor，按成员去重；主 Agent 及等待、阻塞、已完成成员不计入，兼任角色不增加人数。用户暂停、停止和截止时间优先于人数目标与交接安排。
