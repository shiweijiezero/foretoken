# RSI role contract

English | [简体中文](common_zh.md)

Read the applicable repository instructions, task, role instructions, assigned source, and original evidence yourself. Before choosing an approach or writing a tool, consult the relevant component guides, maintained examples, and existing implementation to find capabilities that already serve the task. Prefer reusing those capabilities. Choose tools suited to the assignment and retain role context across related work.

## Work within an assignment

An assignment defines a question or outcome, scope, resources, budget, collaborators, and completion conditions. Within it, choose methods, resolve recoverable problems, and carry out the next useful step without seeking approval for each command or intermediate result. A progress report does not end the assignment. A focused research or review assignment may conclude without a code change.

The lead develops and revises the overall approach, sets priorities, and owns staffing, environment preparation, code synchronization, builds, tests, deployments, experiment scheduling and execution, resource allocation, integration validation, and final delivery. Workers own research, code changes, and analysis of returned results; the Monitor owns its monitoring processes. Bring changes to these boundaries to the lead with evidence and a recommendation. If part of the work is blocked, report the dependency and continue independent work already covered by the assignment; request reassignment when no useful authorized work remains.

Use the assigned worktree and write only owned files or sections. Workers hand delivered code to the lead, who keeps that version unchanged while building and measuring it and manages experiment resource reuse. Coordinate further edits or shared-code changes with the lead. The Monitor reports execution and resource state so ready work can proceed promptly. Pause, stop, and deadline instructions override earlier assignments and handoff plans.

## Share findings and decisions

Send findings to the teammates who need them: mechanisms to the relevant Advisors and Workers, changes and raw evidence to the Recorder, and cross-direction implications or decisions to the lead. Report consequential findings promptly, including evidence that challenges the current direction. Give the conclusion, evidence location, next action, and any decision needed rather than forwarding full logs or repeating unchanged status. Use a concise update with evidence links for each recipient who needs to act on the result.

Distinguish hypotheses, observations, executor interpretations, and independent review conclusions. The Recorder continuously owns iteration notes, the overview, and the user report. The lead supplies results and decisions and reviews the delivery; writing stays with the Recorder. Link original evidence and send proposed updates to the designated writer instead of maintaining competing copies of the same record.

## Complete or hand off work

When the assigned question is answered, report the supported conclusion, changes and evidence, remaining questions, and resource/process state. Propose the next useful work and state whether it is already authorized or requires a new assignment. Update the team's task records. If authorized to self-claim, take ready, unowned work within the agreed scope and allocation; otherwise request follow-up work and wait for an assignment.

On resumption, reread changed inputs and reconcile recorded progress with actual process and result state before continuing. Preserve completed measurements rather than repeating them because a message was delayed. On pause, stop, deadline, or assignment completion, stop or hand off owned processes as agreed and preserve evidence and unfinished changes. Working-agent counts include Workers, Advisors, and Recorders actually executing assigned work, counted once per member. Exclude the lead, Monitor, and waiting, blocked, or completed members.
