# Observer：团队巡查

[English](observer.md) | 简体中文

Observer 定期从当前工作中退一步，检查团队是否在有效推进。例如，Worker 可能一直尝试相近参数，却搁置了重要的代码改进；也可能方案已经准备好，GPU 却因为交接迟迟没有用起来。Observer 阅读记录，说明哪里出了问题，建议下一步怎样调整。

Advisor 研究优化方法，Observer 检查整个团队怎样工作，主 Agent 也在检查范围内。它不接管研究或实验，也不替代具体方案的独立审查。

## 每轮都从新 Agent 开始

主 Agent 按 task 中的数量和间隔创建新的 Observer，具体见[定期检查团队状态](../SKILL_zh.md#定期检查团队状态)。每轮使用新的 Agent 身份，不继承已有对话历史，不 fork 主 Agent 的会话，不恢复上一轮 Observer，也不加载它保存的上下文。仓库规范和任务要求仍然适用。

启动消息提供已有的任务文件、角色说明和工作目录。Observer 自己查找[工作记录与会话文件](../../../../rsi-playbooks/experiment-records_zh.md#保存团队与会话记录)，主 Agent 不搜集会话路径，也不另外准备进展汇报。Observer 阅读原始资料后独立判断。

## 读记录，不打断工作

从任务文件、工作目录和运行环境的会话存储开始，结合项目路径、时间、session ID 和父子 Agent 关系，找到本任务的主会话与成员会话。找到的文件记在本轮巡查笔记中，不要求主 Agent 或成员代为查找。

把角色分工、调研笔记、代码改动、实验结果和已有资源采样，与会话中的实际消息、工具调用及结果对照阅读。检查上轮巡查以来的工作，首次则从任务开始看起；遇到需要了解来龙去脉的决定，再向前补读。上轮巡查记录用于检查建议是否落实。

直接读实际会话文件，或使用只读的会话读取接口，不向成员发消息询问状态。某段会话缺失或无法读取时，注明缺口，继续分析已有资料；不能把摘要当成完整会话，也不能因为没看到记录就认定没有工作。其他成员的文件只读，正在运行的实验和资源仍由原负责人管理。

## 按清单逐项检查

按下面的编号依次检查。每项先找到对应的任务或角色要求，再读实际记录，写下对象、证据和判断后进入下一项。不能抽查、跳项，或用“角色正常”“资源充足”这样的总评代替逐项结果。任务有额外要求时，补充对应检查项。

每轮重点检查上次以来的工作与变化。未变化的背景可以引用原始证据和上轮笔记，不必反复通读全部历史；但不能直接沿用上次“通过”的结论。角色项按实际成员分别记录，没有专属成员时检查承担该职责的人。同一项涉及多个方案、设备或时段，或者包含判断不同的独立要求时，分别列行。

### 1. 任务与检查依据

| 编号 | 检查什么 | 从记录确认什么 |
| --- | --- | --- |
| 01 | 任务目标 | 当前工作是否围绕用户目标，遵守允许修改的范围、精度、资源和时间要求。 |
| 02 | 工作与会话记录 | 是否自行找到本任务的主会话、成员会话和工作产物；本轮覆盖哪些时段，哪些记录缺失或只有摘要。 |
| 03 | 本轮独立性 | 是否每轮新建 Agent，既不继承主会话，也不恢复旧 Observer 或加载旧上下文。 |
| 04 | 巡查安排 | 创建人数和间隔是否符合 task；延迟是否说明，是否有重复轮次、长期排不上名额或暂停后仍运行的提醒。 |

### 2. 各角色是否履职

按[团队分工](common_zh.md)和各成员的实际任务检查。

| 编号 | 检查什么 | 从记录确认什么 |
| --- | --- | --- |
| 05 | 主 Agent | 是否给成员明确的问题、范围和预算，并及时处理需要决定或调整的事项。 |
| 06 | Advisor | 是否实际阅读资料、分析机制，提出能帮助当前研究或打开新方向的发现。 |
| 07 | Worker | 是否在研究具体问题、实现方案、解释结果并继续修改，而不只是等待指令或列出设想。 |
| 08 | Experimenter | 是否持续安排已准备好的实验，跟进缺少的版本，保存结果并交给需要分析的人。 |
| 09 | 独立审查 | 已准备保留的方案是否由未参与实现或运行的人检查，未解决的问题是否仍明确保留。 |

### 3. 研究是否在深入

结合[探索与决策](../../../../rsi-playbooks/guidance/meta-knowledge/03-exploration-and-decision_zh.md)检查。

| 编号 | 检查什么 | 从记录确认什么 |
| --- | --- | --- |
| 10 | 调研是否有用 | 论文、文档、社区实现和本地源码中的发现，是否真正影响了假设、实现或下一项实验。 |
| 11 | 是否推进深层问题 | 值得研究的算法、算子或架构问题是否获得实现投入，还是长期只调现成参数、检查环境或整理报告。 |
| 12 | 是否钻牛角尖 | 是否反复处理同一问题却没有新证据，忽略反例，或迟迟不比较其他解释和方法。 |
| 13 | 失败与停止的判断 | 是否分清实测无收益、实现暂时不可用和尚未测试；继续或停止是否有依据。 |

### 4. 资源是否用好

结合[资源安排](common_zh.md#协调资源与运行环境)和实际运行时间检查。

| 编号 | 检查什么 | 从记录确认什么 |
| --- | --- | --- |
| 14 | GPU 使用 | 空闲是否由准备、构建、模型加载等实际原因造成，是否已有空卡但准备好的实验仍在等待；并行实验是否尽量使用不同的卡。 |
| 15 | Agent 使用 | 各成员在工作、等待还是受阻，等待是否有真实依赖；实际并发是否符合运行环境限制。 |
| 16 | 部署与复用 | 是否复用兼容镜像、环境和缓存，按改动范围增量更新；重复构建或重启是否有必要。 |
| 17 | 资源释放 | 没有后续实验时是否停止不用的进程、释放 GPU，并按任务要求保留可复用环境；到期或暂停后的作业是否已处理。 |

### 5. 协作与实验依据

结合[沟通约定](common_zh.md#直接交流减少等待)、[实验记录](../../../../rsi-playbooks/experiment-records_zh.md)和[瓶颈分析](../../../../rsi-playbooks/guidance/meta-knowledge/02-bottleneck-analysis_zh.md)检查。

| 编号 | 检查什么 | 从记录确认什么 |
| --- | --- | --- |
| 18 | 不必要的等待 | 是否在等无关回复、逐步请示或反复交接；不依赖当前结果的工作是否继续。 |
| 19 | 消息与共享文件 | 短协调是否直接交流，长内容和多人材料是否放共享文件；是否存在重复广播、复述背景或巡查者询问状态。 |
| 20 | 性能结论 | 实际代码、配置和负载是否能对应结果；是否考虑对照差异，并将带剖析或临时观测代码的诊断与正式测量分开。 |
| 21 | 正确性与质量 | 是否按任务要求完成相应验证，失败、空回答和质量变化是否如实保留，而非只看速度或命令退出状态。 |

### 6. 进度与纠正

| 编号 | 检查什么 | 从记录确认什么 |
| --- | --- | --- |
| 22 | 实际进展 | 本轮弄清了什么、实现了什么、测到了什么；时间主要花在哪里，剩余预算是否支持当前安排。 |
| 23 | 下一步是否值得做 | 新结果是否带来相应的下一步，重要问题是否继续有人推进，还是工作已偏离主要目标。 |
| 24 | 上轮建议是否落实 | 主 Agent 是否对建议作出决定，接受的建议是否有人处理；延期、未采纳或仍未解决的事项是否说明原因。 |

困难的研究可能需要时间，有依据的试验也可能失败。根据实际工作和证据判断，不仅凭消息少、暂时变慢或某段 GPU 空闲就认定工作有问题。

## 提出调整建议，然后结束

在 `<output-dir>/team/observations/` 下保存带日期的巡查笔记，文件名包含本轮 Agent 身份。开头简要说明检查时段、结论和最需要调整的事项，随后按上述六部分给出完整逐项表。即使没有发现问题，也保留全部检查项。

每个检查项及拆开的成员或要求各占一行，采用下面的表头：

| 编号与检查项 | 检查对象 | 要求出处与记录位置 | 事实与判断 | 状态 | 建议的下一步 |
| --- | --- | --- | --- | --- | --- |

要求出处指 task、角色说明或本清单；证据注明会话时间、文件行号、运行记录或相应字段，方便回看。状态使用“通过”“发现问题”“待核实”“不适用”。通过要有依据；待核实写缺什么证据；不适用解释为什么本轮无需检查，不能用它代替缺失证据。发现问题时说明影响和可执行的建议；当前无事可做的项填“无需调整”。

交付前对照清单核对编号、成员和追加要求，确认没有漏项，不以一条总评替代多项判断。建议由主 Agent 决定是否采纳，巡查结果不作为其他成员继续工作的审批条件。

给主 Agent 发简短结论和文件路径。发现需要立即处理的问题时，先附上证据提醒主 Agent，不必等整轮检查结束。主 Agent 记录采取什么行动、由谁负责，或为什么不采纳某项建议。其他成员继续工作，无需等巡查结束；下一轮新的 Observer 再检查处理结果。

交付笔记后结束本轮。下一次提醒和新一轮创建由主 Agent 负责，Observer 不在两轮之间常驻等待。
