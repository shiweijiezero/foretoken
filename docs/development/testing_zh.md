# 测试规范

[English](testing.md) | 简体中文

Foretoken 只为关键功能和特征维护少量测试。测试使用真实组件和依赖，尽可能进行端到端（E2E）验证。每次代码修改不要求新增测试。

例如，验证多模型服务时，通过 CLI 部署维护中的配置，分别向两个模型发送请求、检查响应，再删除部署。它验证的是产品特征，而不是手工构造一张路由表后检查字段。这个例子说明如何选择场景，不代表必须新增一项测试。

## 核心准则

### 围绕关键特征，不围绕实现细节

先确定用户依赖的核心能力，再选择少量能够证明该能力的代表性场景。不按函数、源码文件、分支、参数组合或所有可能的故障列出测试清单，不以覆盖率和测试数量为目标。

不维护针对 getter、字段透传、常量映射、薄包装、私有 helper、框架 wiring 或上游内部实现的测试。被选中特征依赖 Foretoken 与上游组件协作时，应验证这条真实接入路径。

### 不使用 mock，执行真实路径

不使用 mock 对象、fake client、stub server、伪造引擎响应或 monkeypatch 替代生产依赖。Fixture 可以提供输入、配置或准备真实资源，但不能实现第二套组件逻辑。

使用特征实际需要的 CLI、服务、Kubernetes 组件、推理引擎和硬件。复用正式的安装、部署、请求、benchmark 和清理路径。测试编排只负责场景准备、执行、断言、诊断和资源回收，不另写安装器、控制器或请求执行器。

优先走完整用户路径。关键特征确实需要局部验证时，直接执行真实实现，并准确说明验证范围。编译、模板渲染和 API server 运行分别验证各自的边界，不代表推理服务已经可用。缺少设备或依赖时，报告场景未执行，不使用模拟结果代替通过。

### 检查实际结果，保持场景内聚

断言响应、配置生效、服务状态、与特征有关的指标和资源清理等可观察结果。不锁定私有调用次数、偶然的执行顺序、完整日志快照或 JSON/YAML 排版。检查结构化资源时，解析其语义字段，不依赖文本出现次数。

一个场景可以跨越多个模块，包含多个相关断言；相互独立的特征应便于分别定位失败，不把 E2E 写成覆盖无关能力的超长脚本。模型质量和性能需要相应的评测或测量，明确负载与硬件条件，不用固定的一句生成文本作为判定依据。

### 优先维护已有测试，不随修改持续增加

先运行相关已有场景。支持的行为变化时，调整调用、输入和预期结果，保留场景原有目的。在旧文件中追加独立场景，仍然属于新增测试。

新增功能、修复 bug、重构和临时排查，都不自动构成新增长期测试的理由。添加测试前，应由维护者明确认可其特征范围和维护价值。一次真实验证可以只留下执行证据，不必转成永久代码或 CI。

## 添加测试的步骤

1. 明确关键特征与预期结果。 说明用户操作和可观察结果，先阅读实现、负责该特征的文档及已有验证。
2. 检查已有场景与新增必要性。 优先重跑或调整已有场景。说明具体缺口，以及反复自动执行为什么值得维护；新增文件、用例、subtest 或独立场景前取得维护者认可。
3. 选择真实执行路径。 找到产品已有入口、实际需要的依赖与硬件，以及最小代表性配置。不为测试方便扩大公共 API，也不在生产代码中增加测试专用开关。
4. 实现场景和清理。 按特征命名，用简短注释说明目的。隔离不同运行的可变资源，用有超时的条件等待观察异步完成；成功、失败和取消后都清理本次拥有的资源。只保留有用诊断，不记录凭据或敏感请求内容。
5. 实际执行并检查结果。 查看响应、状态、日志和清理结果，确认断言能够区分预期结果与具体错误结果。被选中特征涉及恢复时，在隔离的真实系统中触发相应故障，不让替身实现按预设抛异常。
6. 审查后再长期保留。 按下节完成审查，移除临时排查代码，记录实际命令、执行条件和结果。是否接入 CI，依据 [CI 规范](ci_zh.md) 单独决定。

组件测试放在所属 package，按行为命名，不镜像私有模块结构。Rust 组件测试位于 crate 根目录的 `tests/`，不放入 `src/` 内联测试模块；Go 和 Python 使用各自标准的 package 测试位置。跨组件 E2E 编排由相应特征的验证入口维护，不为单个场景建立新的通用测试框架或目录体系。

## 检查测试的步骤

第一轮检查正确性和执行真实性：

- 从测试入口追踪真实的生产者、消费者和清理路径，确认实际运行了什么，是否有替身绕过被测特征。
- 确认断言能够证明该特征，而不只是进程启动、资源存在或配置复制成功。预期结果不能通过复制被测实现来计算。
- 核对状态隔离、有界等待及资源归属，检查失败和取消后的清理。查看实际输出，跳过执行不能算通过。
- 核对测试使用的源码、依赖和产物是否对应当前改动。历史记录或另一条安装路径的结果不是本次证据。

第二轮独立检查范围与维护成本：

- 测试是否仍对应有实际使用者的关键特征？另一场景能否在保留验证含义的前提下覆盖同一行为？
- 删除重复断言、穷举参数矩阵、无关快照、未使用的 helper，以及失去消费者的测试专用依赖。不把 mock 换成自行维护的模拟器。
- 共享准备逻辑保持简单，复用产品已有生命周期。特征行为不变的普通重构，不应迫使测试一起重写。
- 缺少测试本身不是审查问题。产品缺陷应独立给出具体证据，修复缺陷不自动要求新增永久测试。

## 常见错误

| 错误做法 | 应采用的方式 |
| --- | --- |
| 每次修改、每个函数或每次修复都配套测试 | 复用已选定的特征场景，单独判断新增价值 |
| 把新场景藏进已有大测试 | 不论文件位置，都按新增测试审查 |
| 把 fake client 或伪造引擎执行称为 E2E | 使用真实依赖，说明实际执行边界 |
| 在 fixture 中重写部署或推理逻辑 | 调用正式产品入口 |
| 断言生成文本排版或内部对象形状 | 检查特征结果和资源语义字段 |
| 把每个失败分支变成永久场景 | 只选择验证关键特征所必需的场景 |
| 用重试或更长的 sleep 让偶发失败变绿 | 区分产品、测试和环境问题，修复或明确隔离 |
| 场景失效后仍保留调试脚本、fixture 和依赖 | 随旧场景一并清理 |
