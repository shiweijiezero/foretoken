# CI 规范

[English](ci.md) | 简体中文

持续集成（CI）负责调度仓库已有检查和选定的关键特征测试，提供执行环境并报告结果。CI 不维护第二套构建、部署或测试实现。特征选择和真实执行遵循[测试规范](testing_zh.md)。

例如，数据面 workflow 调用 `make verify-data-plane`，而不是单独维护一组 Rust 验证命令。部署特征的场景也应有一个明确归属的入口，开发者和 CI 调用同一实现。纯文档修改不应仅因为项目提供推理服务，就要求运行 GPU 验证。

## 区分职责

| 职责 | 目的 | 执行范围 |
| --- | --- | --- |
| 基础检查 | 格式、静态分析、编译和生成产物一致性 | 针对相关改动，保持快速反馈 |
| 关键特征 E2E | 沿维护中的入口验证真实产品行为 | 选定的特征及其实际需要的环境 |
| 发布自动化 | 构建、验证和发布交付产物 | 当前待发布版本，复用已有构建与验证路径 |
| 通知 | 发送 workflow 或仓库活动结果 | 只报告结果，不实现检查或控制产品行为 |

保留一项测试、安排它在 CI 中运行、将其设为合并必需检查，是三个独立决定。默认不增加常驻任务、workflow、矩阵维度、定时运行或合并门禁。新增功能、修复 bug、临时故障和一次性迁移，都不自动构成新增理由。

## 设计准则

### Workflow 保持简单，执行能够复现

Workflow 准备环境、调用仓库负责该行为的命令、收集诊断并确保清理。特征断言和部署生命周期放在所属验证入口，不堆进 YAML 的长 shell 段落。开发者具备文档说明的依赖后，应能在 CI 平台之外复现同一操作。

复用仓库已有的环境准备与构建路径。多个兼容任务验证同一组源码和依赖时，可以复用同一构建产物，不在每项测试中独立重建，也不使用缓存中的旧二进制。缓存用于依赖和编译工作，不用于复用测试通过结果。

### 按影响和成本选择执行

根据受影响特征及其依赖选择任务。路径过滤需要考虑共享协议、依赖声明与锁文件、构建配置、部署配置和验证入口本身，而不只看最近的源码目录。影响不明确时，选择范围更完整的相关已有任务，不静默漏过。

快速检查与昂贵的集群、GPU、多节点和性能验证分开。选择代表性组合，不穷举模型、硬件、拓扑和参数的笛卡尔积。合适时按需触发；只有已有执行无法满足具体需求时，才考虑定时运行。某次验证采用的设备属于执行条件，不是所有用户的硬件前提。

结果已无使用价值的旧验证可以取消，但应保留清理。发布产物或操作共享环境的任务，应按自身职责确定取消方式，不机械套用同一策略。

### 验证实际交付产物

运行当前改动构建出的包或镜像，确认安装、启动和选定特征沿正式产品路径使用了该产物。直接运行源码不能验证 wheel 或镜像；在运行中的容器里手工修补后成功，也不能证明分发镜像可用。

真实 E2E 使用特征实际需要的依赖和硬件。环境不可用时，报告未执行，不换成 mock、不把错误转成空结果，也不把跳过的场景记为通过。

### 结果可诊断，运行相互隔离

报告实际执行内容、源码或产物版本、必要环境条件及结果，区分产品失败、环境准备失败和未执行。保留有用的命令输出和组件诊断；公开日志不包含凭据、敏感请求内容或内部基础设施信息。

每次运行拥有独立的可变资源，成功、失败和取消后都回收本次资源。共享 runner 上的任务不能修改其他运行的状态，也不能删除其他工作负载。复用已有身份和生命周期机制，不为此另建内容哈希、冻结基线或资源管理框架。

不通过一律重试、无条件成功或吞掉退出码让任务变绿。偶发失败应定位原因；修复期间可以明确停用或隔离不可靠的检查，不把它报告为可信的通过结果。

### 权限与执行来源匹配

任务只使用完成职责所需的权限和凭据。不可信 PR 代码不能带着发布凭据运行，也不能无限制访问共享 GPU runner 和集群。应选择可信执行上下文或隔离环境，不为了绕过 fork 限制而改用高权限事件执行代码。

## 添加或修改 CI 的步骤

1. 确定职责。 说明要验证的基础检查、关键特征或发布产物，先阅读当前 workflow 及其调用的仓库命令。
2. 确认必要性。 说明已有执行遗漏什么、自动化的价值、预期时间和资源开销，以及谁负责排查失败。优先调整已有任务；新增常驻任务、workflow、矩阵维度或定时运行前，取得维护者认可。
3. 选择触发条件和环境。 将共享依赖纳入影响判断，明确实际硬件要求、可信执行边界、并发、超时和清理，判断按需运行是否已经足够。
4. 复用仓库入口。 Workflow 只编排执行。获准的场景确实需要新入口时，由相应验证职责维护，不在 CI 中另写一套实现。
5. 验证真实执行。 在目标环境运行所属命令，检查原始输出和资源清理；在获准的运行中验证改动后的 CI 编排。本地语法检查不能证明 runner 权限、产物传递和触发条件可用，未执行的部分据实说明。
6. 审查，并单独决定合并要求。 按下节检查。设为合并必需检查前，应明确取得对必要性、可靠性、成本、失败负责人和跳过行为的认可，不在添加任务时顺带扩大分支保护。

## 检查 CI 的步骤

第一轮追踪执行与正确性：

- 从事件和变更选择开始，追踪环境准备、构建、产物传递、命令调用、结果报告和清理，确认相关改动能触发应执行的任务。
- 确认运行的是预期产物，依赖是真实组件，权限符合事件来源的可信程度。
- 检查失败和取消路径、超时、日志与清理。环境缺失、上游任务跳过或准备失败，不能表现为特征验证通过。
- 检查过滤、跳过和取消后的合并必需检查状态，既不能虚报验证，也不能让预期检查一直等待。

第二轮独立检查必要性与简洁性：

- 删除重复构建、复制的部署生命周期、嵌入 workflow 的业务断言，以及过时任务或矩阵组合。
- 确认每项任务都有区别于已有检查的当前职责，不为临时排查建立永久基础设施。
- 判断代表性特征执行是否已能提供所需证据，不轻易扩大矩阵、新增调度层或合并门禁。
- 保留发布与通知各自的职责，不因为它们和测试同在 workflow 目录就一并删除。

## 常见错误

| 错误做法 | 应采用的方式 |
| --- | --- |
| 每次改动都增加 workflow 或矩阵维度 | 复用已有任务，单独判断永久新增的价值 |
| 在 YAML 长脚本中写产品断言和部署逻辑 | 调用仓库负责该操作的入口 |
| 用文本计数判断渲染资源是否正确 | 在所属验证路径中断言资源语义 |
| 每个任务重新构建相同产物 | 同一验证组合复用同一产物 |
| 只检查发生修改的源码目录 | 同时考虑共享依赖和交付配置 |
| 将编译、渲染或 dry-run 称为 E2E | 报告实际范围，执行真实特征路径 |
| GPU 场景未执行，却报告特征通过 | 明确报告缺失的执行 |
| 用重试或忽略退出码稳定 CI | 定位原因，保留真实失败结果 |
| 新任务自动成为合并必需检查 | 单独取得扩大合并要求的明确认可 |
