# Foretoken 代码风格

[English](code-style.md) | 简体中文

本文规定 Foretoken 的设计、实现、测试、配置和文档标准。[CONTRIBUTING_zh.md](../../CONTRIBUTING_zh.md) 说明贡献流程，本文说明代码和交付件应达到的长期质量标准。

## 适用范围与权威来源

这些规则适用于 Foretoken 自有代码和发布制品。由上游项目维护的代码，以及纳入仓库的第三方源码，遵循各自项目的约定；Foretoken 自己的适配层仍遵循本文。新增的 Foretoken 源码、配置和脚本文件必须使用仓库统一的 SPDX 许可证声明。

机械性的格式要求和生成文件以仓库内可执行的配置为准。应使用 Makefile、Cargo 配置、Go 工具链、包配置和 pre-commit hooks，不在文档中复制它们的全部选项。本文主要规定格式化工具无法判断的职责归属、边界和可维护性要求。

## 设计与职责归属

在完整说明行为及失败方式的前提下，使用最少的可维护代码。

- 每个类型、辅助函数、配置字段、校验、回退逻辑和测试都应服务于当前职责；删除其使用场景时，也应一并删除。
- 新增抽象前，先消除重复路径，复用现有实现或调用成熟的上游接口。
- 只有存在真实的职责边界，或多个现有实现确实需要共享接口时，才引入 trait、interface、factory、builder 或 registry。
- 同一资源在整个生命周期中应只有一个明确的负责方。资源的创建、使用、清理和状态发布应由该负责方承担；需要移交时，在 API 中明确表达。
- 不在多个运行器、控制器或适配层中复制完整生命周期。复用共同执行路径，各调用者只负责自身不同的策略或输入。
- 共享协议值、默认值、状态转换和派生计算只能有一个定义来源。使用方通过类型化契约或共享辅助函数读取，不复制字符串、数字或算法。

Foretoken 与成熟推理引擎和 Kubernetes 项目集成。在适用时，直接复用其公共接口和由上游完整负责的实现路径。版本敏感或特定后端的行为放入最薄的适配层；平台 API 和通用控制流使用与推理引擎无关的领域类型。

不为当前尚不支持的版本或后端预先加入能力探测、回退逻辑或插件框架。

## 公共接口与配置

公共配置包括 CLI 参数、YAML 字段、环境变量、CRD 字段、API 字段、状态字段和持久化输出结构。新增内容必须对应用户当前确实需要作出的选择，并有实际执行路径使用它。

- 内部修订标识、临时路径、控制器持有的状态、运行时身份、中间结果和编排上下文不作为普通用户配置。
- 可以从模型标识、Kubernetes 资源、Helm 发布实例、命名空间或其他权威输入推导的值，不要求用户重复填写。
- 不通过反射将 struct 或 dataclass 的全部字段自动暴露为公共参数。CLI、配置和参数扫描必须使用显式字段映射。
- 每个默认值只有一个负责方，不在 schema、解析器、控制器、适配层和示例中分别维护同一默认值。
- 用户默认值和运行时默认值应定义在负责它们的配置或生命周期边界。解码器和下游使用方不能用空字符串、空集合、零值或其他便捷回退替代缺失的必需状态；应在负责该契约的边界直接报错，让问题保持可见。只有缺失本身是合法领域状态时，才显式表示为空。
- 实验性能力默认关闭，并明确说明启用方式及其边界。
- 稳定契约不能静默破坏。不兼容变更必须提供明确版本、弃用周期和迁移路径。

YAML 应便于阅读和修改：

- 尽量减少必填字段，让常用配置保持简洁。
- 字段名称应直接说明其控制的对象。有更准确的名称时，避免 `target`、`policy`、`owner`、`extra`、`config` 等宽泛名称。
- 高级选项放入职责明确的嵌套块，不与普通路径混在一起。
- 不用两个字段或两份文件表达同一个选择。
- `values.yaml`、schema、标准示例和用户文档同步更新。
- 用户示例只展示能够完成任务的最小配置，不展开全部可选字段。

## 错误、限制与保障机制

默认不新增校验、固定限制、重试、回退逻辑、哈希、基线或流程门禁。优先使用直接实现、明确的职责归属、类型、版本、主键、事务、唯一约束和普通测试。只有这些更简单的方式无法保护当前实际可能发生的重要失败时，才谨慎增加防御机制。

确有必要增加时，应明确：

1. 哪种输入或运行状态可以触发失败；
2. 哪个组件负责受影响的资源或契约；
3. 判定信号和用户可见结果是什么；
4. 为什么类型、版本、主键、事务、上游校验或普通测试不足。

在负责维护该不变量的边界处只校验一次，不在每个下游层重复相同检查。必需状态缺失和协议失败应清楚暴露，不用空结果或静默默认值伪装成功。

只捕获调用方能够处理的错误。范围过宽的异常处理不应将编程错误、错误使用 SDK 或不变量遭破坏等情况转化为普通远端失败。

## 命名、结构与注释

名称应直接体现领域职责和归属，无需依赖上下文才能理解。优先使用 `create_client`、`metrics_url`、`model_group` 等具体名称，避免模糊动词和通用名词。

值应放在承担其职责的最小作用域。只有一个函数使用的值应定义在函数内；只有多个函数共同使用，或该值代表整个模块的外部契约时，才使用模块级常量。不要仅为了书写方便把配置提升为文件级变量。

将相关步骤组织成一条易读的流程。提取函数时，应对应有意义的阶段或生命周期，而不是仅为了缩短另一个函数。不要把连续逻辑拆成大量薄辅助函数，迫使维护者在多个文件间跳转。

当一个组件需要在多个生命周期阶段持续持有同一组资源、client、配置或不变量时，使用有状态类型表达 ownership：Python 使用 class，Go 和 Rust 使用带方法的 struct。无状态转换和单阶段操作继续使用函数。不要仅为了充当命名空间、缩短参数列表或假设中的复用而引入类型。

以有状态 class 为核心的模块应集中表达该生命周期及其紧密相关的类型。多个当前实现共享的行为放在基类中；adapter 专有的识别、容量判断和策略保留为特化 class 的方法，使一个 adapter 可以在一个位置完整阅读。只有可复用的无状态解析、匹配和格式化放入名称明确的辅助模块。不要机械要求一个文件只能有一个 class；多个 class 共同承担同一生命周期和职责时可以放在一起。

注释说明代码无法直接表达的信息：

- 为什么阶段必须按特定顺序执行；
- 谁负责资源或状态转换；
- 哪个外部契约约束当前实现；
- 失败或清理后必须保留什么状态。

所有一方生产代码中的公开函数都必须有简洁的文档注释，说明它负责什么、由谁调用或使用、返回或发布什么结果，以及重要的资源归属或生命周期。承担完整阶段或无法从名称和签名直接理解的私有函数也需要说明这些信息。生成代码和第三方源码遵循其负责项目的规则。

大块代码、多阶段流程、非直观算法和关键边界必须保留少量结构注释，让维护者先理解执行过程，再阅读细节。

不要为 getter、字段透传、常量映射或显而易见的循环添加注释，也不要逐行注释函数。不要在代码注释中记录修改历史、评审回复、临时计划或实现者的推理过程。

## 语言与仓库工具

遵循相邻代码的既有惯例，以及各子目录配置的可执行检查。

- **Rust 数据面：**运行 `make verify-data-plane`，检查 Foretoken 自有工作区包的格式、编译、测试和 Clippy。
- **Go 控制面：**运行 `make -C control-plane verify`。生成代码和 CRD 通过 Makefile 目标重新生成，不单独手工修改。
- **Python CLI：**公共参数定义和解析应与命令执行分离，跨越该边界时返回明确的命令类型，不传递 `argparse.Namespace`；应在 Kubernetes 环境中实际执行受影响的已安装命令。
- **Python 基准测试：**遵循 `benchmarks/` 中现有的包结构和类型标注风格，运行相关测试，并实际执行受影响的评测命令或运行流程。
- **Helm 与 Kubernetes YAML：**运行 Helm lint，并渲染受影响的模板。把生成资源、values schema、选择器、端口、命名空间和网络访问作为一条部署契约验证。
- **全仓库文件：**运行 `pre-commit run --all-files`，检查文件规范、结构化格式、合并冲突、密钥和 GitHub Actions。

生成文件必须能找到明确的来源。修改来源文件后重新生成制品，不要将生成结果作为另一份实现单独维护。

## 测试

默认不新增测试。编写测试代码前，必须由人类贡献者审查其动机，明确它保护的重要行为或具体回归、现有集成或端到端验证为什么不足，以及维护成本为什么值得承担。无法清楚回答这些问题时，不应新增测试。

测试代码同样需要长期维护，而且很容易快速膨胀。应使用最小测试集合，只保护维护者和用户真正依赖的行为。

- 优先端到端、集成和跨模块契约测试，覆盖真实且完整的关键行为。
- 每个保留的非平凡测试都必须使用准确名称，并在函数前用简短注释说明它保护的契约、具体失败或存在理由。大块测试夹具和多阶段场景应说明整体结构。
- 新建测试模块前，先扩展已有场景、测试夹具或契约测试。
- 对于重要算法、并发、状态转换、恢复路径，以及已经发生且可能复发的缺陷，可以增加聚焦测试。
- 测试 API 响应、CRD 状态、协议事件、指标、资源生命周期和生成部署行为等稳定可观察结果。
- 不测试普通 getter、字段透传、常量映射、无分支薄封装、框架组装代码或已经由上游项目负责的行为。
- 不要仅因新增函数、分支、加载器、状态机或公共方法而机械地补充测试。复杂度和覆盖率数字不是充分理由。
- 不为测试私有实现细节而扩大公共 API。

模型质量、服务性能、GPU 行为或分布式部署发生变化时，代码测试不能替代相应的测量和端到端执行。

## 持续集成

默认不新增常驻 CI 任务、工作流、矩阵或合并门禁。增加 CI 前，必须由人类贡献者审查其动机，明确它保护的当前可达失败、现有检查或直接执行为什么无法暴露该失败，以及谁负责长期维护其运行成本和失败排查。

CI 配置同样容易快速膨胀，也很容易重复环境准备、构建和部署生命周期。优先扩展现有任务、复用仓库中负责该行为的命令，或在相关工作流中运行聚焦检查。不要把临时故障、一次性迁移或假设中的未来回归转化为永久 CI。无法证明必要性和长期维护责任时，不应新增检查。

新增 CI 必须给出可采取行动的失败信息，运行成本应与改动风险相称，并避免重复其他任务或上游项目已经保护的行为。

## 文档

文档面向实际使用或维护最终系统的人，不面向当前 PR 讨论，也不记录作者的实现过程。先确定读者要完成的任务，再决定本页需要哪些背景、命令、选择和结果。

新增或大幅重写用户文档前：

1. 明确页面职责和读者需要得到的结果；
2. 核对当前代码、CLI 帮助、Helm values、schema、维护中的示例、运行行为和清理路径；
3. 阅读至少两个职责相近的成熟项目的最新文档；
4. 先排出最短可执行路径，再写解释文字。

比较成熟项目如何安排前提、首次成功、替代方案、验证和排障。借鉴它们的结构和职责划分，不拼接或复制文字。已弃用、历史、草案和提案文档可以作为背景，但不能作为当前用户文档模板。

每种文档只承担一个清晰职责：

- 根 README 解释项目用途，并提供从准备环境到成功请求和清理的一条默认路径。
- 组件 README 说明用户可见的用途、输入、输出、访问方式和必要限制，不展开源码导览或私有契约。
- 安装、部署、运维、排障和参考指南分别负责自身细节，不在多个入口页面重复维护。
- 维护者文档可以说明 ownership、数据流和取舍，但必须区分当前行为与目标或草案设计。

Quick Start 只保留一条默认成功路径。替代方案放在读者真正需要选择的位置，或链接到负责该内容的指南。不要让每一种安装器、集群类型、访问模式、硬件后端、registry 和高级选项同时打断主流程。

命令和配置示例必须能够直接使用：

- 使用仓库中真实维护的路径、模型标识、字段和默认值；
- 必须使用占位符时，在命令前说明；有现成示例时不使用占位符；
- 要求新增或修改字段时，展示准确的配置片段；
- 只有读者需要依次执行时才把多条命令放在同一个代码块中，并用简短注释标出不同阶段；
- 单条明显命令已有准确标题时，不再用正文重复介绍；
- 不在概览和详细步骤中重复同一条命令。

命令后优先说明用户可观察的结果：安装或部署了什么、需要哪些资源，以及如何判断成功。只有等待或内部生命周期会影响读者何时继续时，才说明这些细节。

新增能力时，先重新审视读者路径，不在原文后机械追加段落。共同行为只写一次，差异放入聚焦小节或负责该内容的指南，并删除被替代、重复或已经失去操作价值的内容。示例、贡献者等会持续增长的列表使用稳定目录或自动维护的入口，不在根文档中手工枚举。

文档 review 是反复迭代的过程。每轮都以首次使用者、有经验的平台运维者和源码开发者的视角通读完整路径。发现具体阅读阻力时，先修页面职责、章节结构和信息位置，再修改句子；随后重读相邻步骤，删除本轮产生的重复。直到默认路径能够执行、替代方案出现在实际选择位置，并且各类读者都没有可达阻塞时结束；达到这些条件后不再做纯措辞改写。

定稿前再单独做一次删除审查，清理重复命令、介绍文档结构的元叙述、位置错误的替代方案、实现细节和没有独立职责的标题。格式检查和测试不能替代人工阅读。

中英文文档在能力、前提、命令、默认值和限制上保持一致，但每个版本都应面向本语言读者独立成文。英文使用自然的技术英语，中文使用自然中文，不逐句翻译。读者需要识别或输入的命令、字段名、类型名和 Kubernetes 资源类型保持原样；不常见术语首次出现时用当前语言说明。

## 变更与 PR 纪律

每个 PR 只承担一项职责，最终差异应以最小且可维护的方式完整实现这项变更。

- 不把功能与无关重构、依赖升级、生成文件漂移或全仓库格式化混在一起。
- 新路径替代旧路径后，删除旧实现、无效配置、重复默认值、过时文档和只保护旧行为的测试。
- 评审前应确认 PR 所基于的分支。堆叠 PR 应说明前置 PR，不能重新引入已经在 `main` 被替换的文件或行为。
- 不提交凭据、私有基础设施信息、个人绝对路径、本地缓存、临时输出或实验产物。
- 只报告实际执行的命令和结果。重要内容未验证时直接说明，不声称执行过实际上未完成的 CI、硬件、Kubernetes 或性能验证。

使用 [.github/PULL_REQUEST_TEMPLATE_zh.md](../../.github/PULL_REQUEST_TEMPLATE_zh.md) 说明问题、改动、验证证据、性能表现、影响及关联议题或提案，不在 PR 描述中复制本文。
