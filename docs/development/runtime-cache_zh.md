# 运行时缓存生命周期

[English](runtime-cache.md) | 简体中文

部署配置见[模型存储](../features/model-storage_zh.md)。

## 存储职责

RuntimeCache 选择命名空间内的 PVC，并发布其就绪状态。管理员准备的命名空间通过目录绑定授权访问；RuntimeCache 只使用对应 PVC，不接管或删除它。显式目录选择优先于管理员设置的默认 claim。成员无需访问 PV 或其他命名空间。

自行管理的目录部署由 CLI 解析节点可见路径，在控制器创建 PVC 后准备静态 PV。本地 k3d 的调度范围来自节点的实际绑定挂载；跨节点目录必须向各消费者提供同一文件系统。

动态缓存通过 StorageClass 申请存储。配置 `maxSize` 后，控制器在各挂载点观测到的最低空闲比例达到 20% 时申请扩容，将容量逐次翻倍至上限。扩容失败时，工作负载仍可使用已绑定的卷。

## 模型引用与回收

使用模型 X 的服务在暂停后仍保留来源引用。删除服务时，先等待准备任务和运行实例退出，再释放引用。另一个使用 X 的服务会继续保留 X；仅使用 Y 的服务不会阻止 X 回收。

Pool 将选中的来源记录与副本数量分开保存，旧运行批次在排空期间继续保留各自的来源。下载流程在访问共享文件前发布固定的模型和 tokenizer 版本，因此进程重启不会让已有引用随远端分支移动。

每个模型缓存根通过稳定的文件锁协调准备与回收。根目录中的持久身份区分独立目录，同时识别指向同一数据的命名空间 PVC 和挂载别名。回收流程持有排他锁，重新读取当前来源引用后，才删除来源缓存中的快照及无引用的数据文件。自备模型不放入这一区域。

平台负责回收任务及其临时存储绑定，命名空间控制器负责服务意图和来源记录的退出。原生 NFS、NFS CSI 与目录型 hostPath 可通过独立的 Retain 卷别名访问，原卷保持不变；其他动态存储由存储驱动管理生命周期。回收完成后，先清理任务与卷别名，最后释放来源记录。

## 缓存布局与应用更新

当前应用将来源下载放在 `shared/models`，可变运行状态放在 `namespaces/<namespace>`，自备模型放在 `models`。Hugging Face 账号状态与共享 Hub 文件缓存分开保存；模型仓库中的配置和 tokenizer 文件属于模型资产，与运行配置区分。

应用选择同时固定可执行程序与准备协议。已有应用在显式部署采用新应用之前，保留原来的输入和缓存布局；仅更新控制器，不会把新准备协议发送给旧镜像。

Triton 使用命名空间内的 `triton/<节点名>`，隔离不同节点的写入，并在 Pod 重建后复用。引擎自身的编译器子目录仍由推理引擎管理。单节点服务的持久缓存写入检查失败时，model-server 会停止失败的 EngineCore，再用 Pod 内临时存储重试；仍可读取的持久模型文件可以继续复用。多节点成员统一重启。

性能剖析发布到 `namespaces/<namespace>/profiles/runs`。每个采集计划保存实际输出目录，也包括旧应用采用的原目录。查看器读取当前命名空间的结果及历史记录明确保存的单次采集路径；临时缓存重试期间不提供性能剖析。

## 卷的保留

保留 RuntimeCache 时，控制器移除 PVC 的归属，让后续兼容缓存可以重新接管。删除 Namespace 仍会删除其中的 PVC。目录 PV 使用 Retain，删除 Kubernetes 对象不会递归清理自备文件或命名空间运行状态；托管模型下载按前述引用生命周期单独回收。

设置 `retentionPolicy: Delete` 时，RuntimeCache 控制器等待工作负载释放 PVC 后完成删除，CLI 随后删除自己管理的目录 PV 对象。动态卷遵循 StorageClass 的回收策略。重新绑定保留的目录卷时，使用已观察到的 claim UID 和资源版本，避免覆盖并发绑定。
