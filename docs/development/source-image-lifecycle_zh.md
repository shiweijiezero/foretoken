# 源码部署生命周期

[English](source-image-lifecycle.md) | 简体中文

本文说明维护源码部署功能时应保持的行为。安装、部署和并行实验的命令见[从源码部署 Foretoken](../custom-deployment_zh.md)。

## 安装与更新

平台安装负责共享 CRD、依赖和默认运行环境，并准备初始应用构建。部署从选定的代码目录构建控制器、前端及模型服务，更新本次提交的命名空间。各命名空间的控制器只管理本命名空间的资源，因此控制器代码与服务代码通过同一部署入口更新；CRD 变更仍需重新安装平台。

源码更新复用兼容的运行环境，依赖或基础镜像输入变化时自动重建。CLI 为每个 Foretoken 源码目录分别记住引擎目录。引擎源码需与选定的 Python、PyTorch 和设备库兼容。

## 构建与发布

Go 控制器、Rust 服务程序、Python 适配文件和推理引擎文件分别依赖各自的构建输入。只重建受改动影响的部分，整体替换对应产物，包含文件删除。其余文件从与先前输入和运行环境一致的已完成应用中复用。完整应用发布后再更新服务；运行中的服务不依赖可写的编译缓存。

编译缓存可在构建器重建后继续使用。显式选择的构建存储类保存已完成产物，执行状态仍放在自动管理的本地存储。发布只读取完整导出，源码归档读取对应的本地工作区；两张构建卷随同一构建任务清理。应用和模型存储保留各自的配置与生命周期。

独立源码目录可以并行构建。同一源码目录内的准备和提交串行执行，平台安装、卸载与这些操作互斥。等待服务就绪时，应允许删除操作释放已占用的设备。

完整发布包含压缩归档，安装时一次下载，按清单核对文件后再替换正在使用的应用；已有的逐文件发布仍可读取。CLI 取得发布 Job 的 Kubernetes UID 后，才提供该 Job 的执行输入。这样，即使创建请求在取消后才完成，任务也不能自行发布或回收文件。

只有 Helm 清单与集群中的声明字段都一致时，无变化部署才复用命名空间控制器。服务的应用选择随控制器或应用更新而变化，不因重复执行 CLI 而变化。首次前端等待选定的运行缓存就绪后再启动，避免先创建临时实例、随后再次滚动更新。

## 就绪与失败

选定的应用和服务路由均就绪后，部署才成功。滚动更新和请求排空由控制器管理。服务状态观察与源码生效确认共用一个截止时间，源码编译仍是独立阶段。CLI 的等待预算同时约束控制命令和获取锁的等待，但不会使正在执行的持锁操作失效。

模型的启动设置分别约束准备和运行工作负载。准备失败后，即使原生 Job 正在重试，失败仍保留到准备成功。前端配置被拒绝时也会结束 CLI 等待；可恢复的工作负载和 API 等待继续按进行中处理。

并行阶段共享取消状态并保留首个失败原因。资源所有者先停止进程及发布任务，再等待工作线程退出。清理使用独立的有限等待时间，观察超时不会阻止释放锁或删除已创建的资源。

## 清理

构建失败或取消时，停止相应构建器和发布任务，保留编译缓存供重试。清理时保留部署、构建或回滚仍需使用的应用，释放闲置资源前保存可恢复的构建输入。

`foretoken delete` 先等待服务和工作负载完成清理，再移除不再使用的命名空间控制器。提交的配置中若包含命名空间，则在最后删除。命令同时回收不再使用的构建资源，保留源码目录、实验结果和源码归档。

部署全部删除后再卸载共享平台，先回收编译卷，再移除供卷组件。模型数据和输入归档保留。
