# 16 — Qwen3.6-27B 评测发现(真实对话 trace 的 goodput 评测)

基于 foretoken 评测台对 Qwen3.6-27B 的一次系统评测(2026-06-09,A100 80G,vLLM 0.22.1)。
负载为 `foretoken-trace`(conversation / mooncake / toolagent 三种真实多轮对话画像),时间窗 0:20
(真实节奏),SLO 阶梯严/中/松 = 2000:80 / 10000:150 / 60000:200(TTFT:TPOT ms)。核心指标为
**goodput@SLO**(满足延迟 SLO 的输出 token/s,即「可交付」吞吐)与 **$/Mtok@SLO**(每百万可交付
token 成本)。结论用于校准 docs/03(价值函数)、docs/11(goodput 调度)、docs/15(token 工厂路线)。

> 模型为**混合注意力**(Mamba 线性层 + 满注意力层),`Qwen3_5ForConditionalGeneration`,bf16 约 52G,
> 单 A100 可跑。下文「卡」均指 A100 80G;成本按参考云上按需价 A100 ≈ $1.8/GPU·h(用 `--gpu-rate` 可改)。

## 1. 单引擎在该 trace 上很快拥塞崩溃,goodput 在 r10 见顶

conversation,单卡,按到达率(req/min)扫描:

| rate | 达成@严 | good tok/s | out tok/s | 取消会话 | TTFT p50 |
|---|---|---|---|---|---|
| 5 | 98% | 180 | 182 | 0 | 0.19s |
| 10 | 96% | **334** | 347 | 0 | 0.26s |
| 15 | 66% | 328 | 435 | 3 | 0.39s |
| 20 | 39% | 200 | 441 | 13 | 22s |
| 40 | 21% | 108 | 485 | 302 | 320s |
| 60 | 16% | 76 | 455 | 651 | 258s |
| 80 | 10% | 60 | 521 | 873 | 454s |
| 120 | 5% | 54 | 545 | 1462 | 498s |

原始吞吐(out tok/s)随负载升至 ~485-545 的容量天花板即不再增长,但 **goodput 在 r10 见顶(334)后随
负载单调下跌**:超过 ~r15 后排队累积,TTFT 从亚秒跳到数百秒,会话被 deadline 大量截断。**典型拥塞崩溃**
——对 token 工厂的含义是:盲目堆并发不增「可交付」吞吐,只增尾延迟与浪费。运行点应锁在 goodput 拐点附近。

## 2. 扩到 2 卡:健康区 TP≈DP,饱和后 TP 明显更优雅

conversation,2 卡,张量并行(TP=2,单引擎跨 2 卡)vs 数据并行(DP=2,两独立引擎 least-loaded 路由):

| rate | TP good/s(达成) | DP good/s(达成) |
|---|---|---|
| 20 | 554 (100%) | 545 (96%) |
| 40 | **732** (62%) | 439 (45%) |
| 60 | 437 (25%) | 305 (25%) |
| 80 | 312 (17%) | 216 (19%) |
| 120 | 248 (15%) | 212 (18%) |

- **健康区(r20)TP 与 DP 基本等价**(554 vs 545):都只是从容服务既有负载。
- **进入饱和(r40+)后 TP 持续领先 ~40-67%**,且 TP 峰值(732@r40)高于 DP 峰值(545@r20)——TP 能在
  崩溃前吸收更高负载。
- **峰值 goodput 扩展比**:1 卡 334 → TP2 732(2.2×)、DP2 545(1.6×)。TP 扩展更优。

成因:TP 把 2 卡的 KV/计算池化为单队列、保留完整前缀缓存;DP 把请求分到两引擎,**每引擎 KV 减半、
前缀缓存不跨引擎、同会话多轮可能被路由到不同 rank 而丢失 KV 复用**。对 KV 复用重的对话负载,这些在
饱和时放大为劣势。**这为「价值/亲和感知的 KV 路由」(docs/15 差异化方向 4)提供了直接证据**:DP 的损失
正源于路由对 KV 复用不敏感。

## 3. 前缀缓存在混合模型上「健康帮、饱和害」,交叉约在 r15

conversation,单卡,前缀缓存开(base)vs 关(noprefix):

| rate | base good/s(达成) | noprefix good/s(达成) |
|---|---|---|
| 10 | 334 (96%) | 322 (86%) |
| 20 | 200 (39%) | **249 (49%)** |
| 30 | (近 base) | 215 (29%) |
| 40 | 108 (21%) | **162 (27%)** |

- **健康区(r10)开前缀缓存略好**(334 vs 322):有空闲 KV 时复用前缀省 prefill。
- **饱和区(r20+)关前缀缓存反而更好**(r40:162 vs 108):KV 紧张时,被前缀缓存占住的块与运行中请求争抢,
  加上混合模型**只有满注意力层能前缀缓存、Mamba 态不能**,管理开销 > 复用收益。
- **vLLM 对 hybrid 模型默认关前缀缓存是合理的**;当前 `config/models/Qwen3.6-27B.toml` 强制开
  (`enable_prefix_caching=true`)在受载服务下是负优化。**建议:除非确认低负载且复用率高,否则按默认关**,
  或做成负载自适应(低载开、高载关)——这本身是一个 goodput 调度的小钩子(docs/11)。

## 4. KV-connector 类特性(KV offload / disaggregated P/D)在该混合模型上被上游封禁

尝试 CPU KV offload(`kv_offloading_size`,native `OffloadingConnector`)时,引擎可启动并开始服务,
但很快崩于:

```
vllm/v1/core/sched/scheduler.py  _mamba_block_aligned_split
AssertionError: External KV connector is not verified yet  (num_external_computed_tokens == 0)
```

Mamba 块调度器**显式拒绝任何外部 KV connector**。由于 KV offload 与 disaggregated P/D 都依赖外部 KV
connector(offload 走 OffloadingConnector,disagg 走 P2pNccl/NIXL 等),**两者在 vLLM 0.22.1 上对
Qwen3.6-27B 这类 Mamba 混合模型均不可用**。

**对 docs/15(token 工厂路线)的关键约束**:阶段一/二里「KV offload(P1 主战场)」与「vLLM 原生 1P1D」
**只适用于标准注意力模型**;对混合/Mamba 模型,这些 KV 编排能力要么等上游支持,要么换机制(如 LMCache),
要么改在满注意力层做。价值感知 KV 策略(P1)的挂载点 `v1/kv_offload/cpu/policies/base.py` 同样受此限制。
**选型含义**:若 token 工厂要用 KV offload / disaggregated 作为核心杠杆,模型侧应优先标准注意力架构,
或把混合模型的 KV 编排列为需要上游协作的明确风险项。

## 5. 计价成本:同载下 2 卡每「可交付 token」更便宜

`$/Mtok@严SLO` = 运行成本 / 满足严 SLO 的百万 output token(运行成本 = GPU 数 × 时长 × 时价):

| 配置(r40,0:20) | GPU | 达成@严 | good tok/s | **$/Mtok@严** |
|---|---|---|---|---|
| TP=2 | 2×A100 | 62% | 732 | **$1.37** |
| DP=2 | 2×A100 | 45% | 439 | ~$2.3 |
| 单卡 | 1×A100 | 21% | 108 | **$4.65** |
| serve-dp1(1 引擎占 2 卡) | 2×A100 | 21% | 119 | $8.40 |

**虽然 2 卡硬件成本翻倍,但同样 rate 40 下 TP=2 每可交付 token 便宜 3.4×**:单卡产出的 token 大多违 SLO
(不可交付),而 2 卡把它们拉回 SLO 内。token 工厂的定价基准应是 **$/Mtok@SLO** 而非原始吞吐——原始口径
会误判「单卡更省」。`serve-dp1`(2 卡只起 1 引擎)是反面教材:按 2 卡计费却只用 1 引擎,最贵。

但把每个配置**放在各自的 goodput 拐点**上看,结论更精确——成本由「是否运行在拐点」决定,而非单纯卡数:

| 配置 @ 各自拐点 | $/Mtok@严 | 达成 | good tok/s |
|---|---|---|---|
| TP=2 @ r40 | **$1.25–1.42** | 51–63% | 702–801 |
| 单卡 @ r10 | $1.50 | 96% | 334 |
| DP=2 @ r20 | $1.83 | 96% | 545 |
| 单卡 @ r40(过载) | $4.65 | 21% | 108 |
| 单卡 @ r5(欠载) | $2.78 | 98% | 180 |

**单卡跑在甜点 r10($1.50)几乎和 TP=2($1.37)一样省**;真正贵的是把任何配置跑到过载($4.65)或欠载
($2.78)。TP=2 的拐点经济性最好(峰值 goodput 高、单位成本低),但「锁定拐点」比「堆卡」更重要。
**TP>DP 经方差确认**:tp2-r40 三次重复 good 702/732/801(~745±50),dp2-r40 四次重复 439–474(~462±15),
两区间不重叠。

## 方法学与局限

- 回放真实时间戳、真实多轮(整会话保留),deadline = 窗口 × 2 截长尾;高负载下大量会话被截断(取消列),
  其 goodput 反映「该配置在此负载下不可持续」,是有效信号而非缺陷。
- 单实例评测(集群级 trace 经会话级下采样匹配硬件);未含跨实例亲和路由。
- **未测 4 卡**:本次集群无任一台有 4 张连续空卡,TP4/DP4 的 r80 是否回到健康区留作后续。
- offload-on 为崩溃残值(11 请求即挂),不计入分析。
- 数字为本机本次实测,换硬件(如沐曦)须重测(docs/15)。

## 对路线的启示

1. **TP > DP(饱和区)直接支撑价值/亲和感知 KV 路由**(docs/15 差异化 4):DP 的损失来自路由对 KV 复用不敏感。
2. **混合模型封禁 KV-connector** 重塑 offload/disagg 计划的适用边界(docs/15 须补此约束)。
3. **前缀缓存负载自适应**是一个小而实的 goodput 钩子(docs/11)。
4. **$/Mtok@SLO 是工厂经济学的正确标尺**;评测台已内建(`report/cost.py`)。
5. 运行点应锁在 goodput 拐点附近,而非堆并发——拐点定位正是评测台的价值。
