# 指标定义

每次 run 的指标落 `run.json`(机器可读)与 `summary.md`(人读 + 内嵌图),分为延迟、生成速度、吞吐、goodput、成本、引擎监控几组。

## 延迟

- **TTFT**(首 token 延迟):发出请求到收到第一个 token。
- **TPOT**(逐 token 间隔):decode 阶段相邻 token 的平均间隔。
- **E2E**(端到端):整轮从发出到完成。

三者各报 p50 / p90 / p99。**尾部比** = TTFT p99/p50,反映过载下的尾延迟膨胀。

用户感知由两个正交轴构成:TTFT(发出到见到首字的**等待**)+ 生成速度(见下,出字的**流畅度**)。

## 生成速度(用户感知)

单个用户的出字速度 = `1000 / TPOT`(tok/s),即 TPOT 的倒数视角,更直观地表示「开始看到回复后每秒吐多少 token」。只要它 ≥ 人的阅读速度,用户即无感等待。关注其**慢尾**(对应 TPOT 的高分位)——慢的那批请求决定体感底线。

## 吞吐

- 输出 / 输入 / 总(输入+输出)tok/s,及输出 /GPU。
- 完成 req/s。

原始吞吐不按 SLO 过滤:过载时仍然很高,但大量 token 不可交付,因此必须与 goodput 对照看。

## goodput@SLO

满足 SLO(TTFT ≤ 阈值 **且** TPOT ≤ 阈值)的有效输出 tok/s,**只计完整完成的请求**。按严 / 中 / 松 SLO 阶梯报告(`--slo TTFT_ms:TPOT_ms` 自定义),每档给:

- **达成率** = 达标轮 / 完成轮。
- **good tok/s** 及 **/GPU**。
- **归一化** tok/(s·GPU字节) = 达标 token / (时长 × GPU 字节),把策略与硬件规模隔离,使不同配置可比。

原始吞吐随负载升到容量天花板即不再增长,但 goodput 见顶后随负载单调下跌(拥塞崩溃);goodput 拐点即可持续运行点。

## ¥/Mtok@SLO

每百万可交付 token 的成本 = (GPU 数 × 时长 × GPU 时价) / (满足 SLO 的百万 output token)。

- 按 SLO 阶梯报(达成口径只计可交付 token);另给一个原始口径(不按 SLO 过滤)作对照。
- GPU 时价按 GPU 型号解析,可配置。
- 这是 Token 工厂经济学的正确标尺:裸吞吐口径会误判「卡少更省」——过载下单卡产出的 token 大多违 SLO、不可交付,折算到可交付 token 反而最贵。

## 引擎监控(后端提供时)

进程内后端逐 iteration 采集引擎调度器统计:

- **KV cache 利用率**(峰值 / 均值 + 随时间)。
- **运行中 / 排队** 请求数随时间。

用于判断瓶颈在引擎(KV 占满、排队累积)还是客户端发送侧。外部 API 后端无逐 iteration 引擎监控。
