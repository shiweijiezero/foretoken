# 架构与扩展

## 定位

Foretoken 是一个真实负载 goodput 评测台,以及在其之上的一组推理优化策略。北极星指标是 **¥/Mtok@SLO**(每百万可交付 token 的成本)——衡量一套配置把 GPU 变成「满足延迟 SLO 的 token」的效率,而非裸吞吐。愿景是成为 Token 工厂(高效 token 生产)的质量度量与优化层。

设计上分两块:**评测台**(后端无关、可复现地度量任意配置)与**优化策略**(KV 管理、投机解码、调度等可插拔模块)。两者解耦:评测台不假设被测的是哪种优化,优化模块也不绑定某一评测流程。

## 核心模块

| 模块 | 职责 | 代码 |
|---|---|---|
| **回放核心** | 加载负载、时间窗截取、会话级下采样、闭环时间调度、goodput 标尺 | `foretoken/bench/core/` |
| **执行后端** | 把回放请求送到引擎并采集逐轮指标;进程内引擎或外部服务 | `foretoken/bench/core/`(`vllm_engine` / `backend`) |
| **报告** | 聚合延迟分位 / 吞吐 / goodput / 成本 / 引擎监控,出 `summary.md`、双语图、排行榜、对比 | `foretoken/bench/report/` |
| **数据准备** | 把生产 trace 与多轮对话缝合为可复现负载 | `data_prepare/` |
| **优化策略** | KV 管理、投机解码、调度等被评测的优化(见[路线图](roadmap.md)) | 随各模块落地 |

## 后端无关

闭环回放的核心逻辑——按真实 timestamp 调度、会话化、用模型现场回复拼接下一轮——与执行后端解耦。同一套回放可发往三种后端,区别只在请求送到哪、测到哪一层:

| 后端 | 测什么 |
|---|---|
| 进程内(默认) | 纯引擎能力(KV / 调度 / 解码)+ 逐 iteration KV%/并发监控 |
| `--endpoint URL` | 全生产栈(HTTP + 前端 tokenize/detok + 前端进程数 + DP 路由) |
| `--serve` | 同上,但 bench 自起服务、回放完整后收尾释放 GPU |

后端通过一个窄接口接入(给定一组消息与请求 id,流式产出 token 与计时)。当前参考实现是 vLLM(进程内 `AsyncLLM` 或外部 `vllm serve`);接入其它后端只需实现同一接口,回放、指标、报告层不变。

## 可扩展设计

评测台与策略框架遵循一组通用的可扩展原则,使外部能插入自定义后端、优化策略或负载,而无需改动核心:

- **分层开放、热路径封闭**:配置层全开放;中层以抽象基类(ABC)定接口契约、由实现方提供;性能热路径与正确性关键处封闭,不做运行时替换。
- **优先级链**:用户代码 > 外部插件 > 内置实现,允许覆盖而不改源码。
- **契约 + 延迟加载**:框架定接口、调用方自带实现并以限定名延迟加载,框架不关心实现细节,便于 mock 与独立测试。
- **逃生舱**:对少数无命名扩展点的情形,提供「传任意实现类路径」的通用接口兜底。

这组原则同样指导被评测的优化模块:KV 策略、调度策略、投机控制器都设计为可替换的策略对象,以便在同一评测台上做受控 A/B 对照(见[评测指南](evaluation.md))。
