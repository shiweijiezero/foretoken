# 按层组推进 MoE 预填充

[English](layered-prefill.md) | 简体中文

在预填充与解码共置的 MoE 服务中，按连续层组推进预填充，可以减少小 token 分块反复读取专家权重的开销，同时给已有请求保留解码机会。

## 思路

### 为什么要拆开预填充

预填充（prefill）一次处理请求的输入序列，建立各层的 KV 缓存；解码（decode）随后逐个生成 token。当两者共用一组 GPU 时，新来的长输入会占用较长计算时间，使正在解码的请求等待。

Chunked prefill 沿 token 维度拆开长输入：每轮处理一小段输入，同时推进已有请求的解码。这样可以缩短单轮计算时间，但每段输入都要经过全部模型层。

对 MoE，这会带来额外的专家权重读取。单个 token 只选择少量专家，但一段输入中的多个 token 合起来可能选中大部分专家。于是，每个小分块都读取一批近似相同的专家权重，每个专家却只处理少量 token。这里的读取主要指 GPU 从显存读取权重，权重可以始终驻留在 GPU 上。

### 换一个拆分方向

Layered prefill 保留较大的输入批量，改为拆分模型层。一轮只让新请求的预填充经过一组连续层；下一轮从该组的输出继续。已有解码请求每轮仍经过全部层，生成下一个 token。

用 4 层模型和 8 个输入 token 说明两种顺序。按 token 分块时，每块 4 个 token；按层分组时，每组 2 层。以下表格只列新请求的预填充工作：

| 调度轮次 | 按 token 分块 | 按层组推进 |
| --- | --- | --- |
| 第 1 轮 | token 1–4 经过层 1–4 | token 1–8 经过层 1–2 |
| 第 2 轮 | token 5–8 经过层 1–4 | token 1–8 从保存的状态继续经过层 3–4 |

在层组调度的第 1 轮，层 1–2 同时处理预填充和解码，层 3–4 只处理解码；第 2 轮则反过来。新请求完成全部层组后，才能生成自己的第一个输出 token。两种方式都完成所有输入 token、所有层的计算，改变的是工作在轮次之间的分配。

### 为什么 MoE 可能更快

以上表的某一个 MoE 层为例：按 token 分块时，该层分两次处理输入，两个分块都可能触发同一批专家的权重读取；按层组推进时，该层一次处理全部 8 个输入 token，读取的专家权重可以服务更多 token。

收益取决于分块之间的专家重合度，以及每次专家计算能否充分利用读入的权重。它减少的是小分块引起的重复访存开销，而不是 token 必须执行的模型计算。实际服务中，已有解码请求仍需读取它们选中的专家权重。

超长输入可以同时使用两种拆分：先切成较大的 token 分块，再让每块按层组推进。这样既控制中间状态的显存占用，也保留较大的每专家计算批量。

## 适用场景

- 预填充与解码共置，有长 prompt 持续进入，同时需要控制已有请求的 token 间隔。
- MoE 的小 token 分块激活了较多专家，专家权重读取成为明显开销；解码批量较小时更值得调查。

按层暂停和恢复的思路不绑定一种 GPU，但论文收益依赖 MoE 专家访问模式。作者在稠密模型 Qwen3-8B 上观察到退化；放宽 token 间隔要求、允许更大的 token 分块后，两种调度的差距也会缩小。只有单个请求、prefill 已完成且没有新 prefill 插入时，这个机制没有额外的 prefill 权重读取可以消除。

## 实现线索

[公开实现](https://github.com/scale-snu/layered-prefill/tree/053f80e5201a7c0ab56e468e3d578907a2ca9cc3)基于 Nano-vLLM，提供层组调度及基准命令。

vLLM 的[调度输出](https://github.com/vllm-project/vllm/blob/1be36283678a9a94fc8fdaad6c95c2896d6b4015/vllm/v1/core/sched/output.py)中，工作量按每请求 token 数表达；[Qwen3 MoE 执行路径](https://github.com/vllm-project/vllm/blob/1be36283678a9a94fc8fdaad6c95c2896d6b4015/vllm/model_executor/models/qwen3_moe.py)遍历当前流水线阶段所属层。层组调度需要在这些接口之间传递请求的层进度，并保存跨轮恢复所需的状态。

迁移时需要设计以下执行状态：

1. 调度器分别记录请求的 token 进度和层组进度。一个层组结束后，输入尚未经过全部层，不能将它当作完整的预填充结果。
2. 模型执行入口支持指定层范围。暂停时保存该组输出的隐藏状态、所需残差，以及位置和 KV 映射；后续层组继续使用它们。已经完成的层保留各自的 KV 缓存，尚未执行的层继续等待预填充。
3. 将这些跨轮状态纳入抢占、取消、批次重组和 CUDA Graph 管理。层组越大，单轮预填充工作越多，解码等待可能越长；层组越小，轮次和状态管理开销越多。需要一起测量首 token 延迟、解码间隔和中间状态显存。

先用相同请求轨迹比较 token 分块与层组调度，观察 TTFT、token 间隔尾延迟、显存峰值及专家权重读取。对比时保持模型和采样条件一致，并检查输出一致性。在混合服务负载下测量端到端收益。
